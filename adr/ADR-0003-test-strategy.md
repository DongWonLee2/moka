# ADR-0003: 테스트 전략과 시계 주입

- 상태: Accepted
- 작성일 / 사람 승인일: 2026-10-28 / 2026-10-28
- 결정 책임자: 저장소 소유자
- 관련 Spec/R-ID: PRD FR 수용 기준, 7장 정책 1~5, FR-16(하루 시작 시각), FR-18(튜닝 스크립트), 헌법 II
- 사용한 외부 근거: swift-testing README(리눅스 지원)

## 맥락

시간에 기대는 규칙(06:00 경계, quantum 만료, 연장, 일시 중지)이 많고, 실제 시간을 기다리는 테스트는 금지다(헌법). 테스트는 리눅스 CI와 밤 무인 실행에서 돌아야 한다. 의존성은 승인된 3개 밖으로 늘리지 않는다. (정정: DynamicNotchKit은 ADR-0008로 제외)

## 평가 기준

1. 리눅스에서 실제로 돈다는 실측 2. FR·정책 번호 추적 3. 시간 규칙을 결정적으로 시험 4. 의존성 추가 없음

## 대안

| 대안 | 장점 | 단점·위험 | 근거·실험 |
|---|---|---|---|
| A. Swift Testing(앱 UI만 XCTest), 시계는 클로저·`Calendar` 주입 | 매개변수 테스트, 표시 이름으로 ID 추적, 의존성 없음 | 병렬 기본 실행 → 공유 파일 DB 간섭 | `swift:6.3.3-noble`에서 Swift Testing 테스트 PASS |
| B. XCTest만 | 익숙함 | 매개변수 테스트가 번거로움 | — |
| C. swift-clocks 같은 시계 라이브러리 | 기능 풍부 | 새 의존성 → 승인 필요 | — |

## Agent의 추천과 근거

A를 추천한다(추천안 토론 3:0).
- `MokaCore`·`MokaStore` 테스트는 Swift Testing. 표시 이름은 FR·정책 번호로 시작한다(예: `@Test("FR-05: …")`). 앱 UI 테스트만 XCTest(XCUITest).
- 시계: `MokaClock`(현재 시각을 돌려주는 작은 타입, 표준 `Clock`과 이름 충돌 회피)과 `Calendar`(시간대 포함)를 주입한다. `MokaCore` 안에서 `Date()`·`TimeZone.current`를 직접 읽지 않는다.
- 하루 경계는 설정 `day_start`(기본 06:00)와 주입한 `Calendar`로 계산한다. 앱은 `Calendar.autoupdatingCurrent`, 테스트는 `Asia/Seoul`과 일광절약시간이 있는 `America/New_York`을 고정 주입한다. (정정: 이 문장은 [ADR-0010](ADR-0010-day-boundary-calendar.md)이 대체한다.)
- 타이머는 실제로 잠들지 않는 상태기계다. 시각을 붙인 이벤트(`tick(now:)` 등)로만 상태가 바뀐다. 저장 시각은 UTC.
- 튜닝 스크립트(FR-18)는 pytest와 가짜 SQLite 파일. 실제 decision API는 가짜 공급자로 대신한다.
- 검증 경로: `moka-sim`(시나리오 JSON 입력 → 하루 배정과 로그 출력). 노치 화면은 사람이 확인한다.

## 사람의 최종 결정과 실제 판단 이유

Agent 추천안 채택. 판단 이유: 사용자 위임(토론 채택안 "전부 승인", 2026-10-28)

## 포기하는 것·운영 영향

- 트레이드오프: 시간대를 옮겨 다니는 사용(여행)은 범위 밖이다. "오늘"은 시스템 시간대 기준이다. 잠자기에서 깨어날 때의 경계 판정은 별도 설계가 필요할 수 있다.
- 되돌리기: 쉬움(테스트가 적은 초기).

## 결정 검증

- 실행할 실험: 기대값을 일부러 틀리게 바꿔 CI가 FAIL하고 종료 코드가 0이 아닌지 확인(커밋하지 않음).
- 성공 판정: 주입 시 FAIL, 원복 시 PASS.
- 재검토 트리거: 리눅스에서 Swift Testing 발견·실행 실패, 테스트끼리 공유 상태로 간섭.
