- **Q1~Q6**은 갈림이 커서 plan "확정할 것"에 선택지만 적었고, 2026-11-16 메인 세션 debate와 사람 결정으로 정했다(기록 저장소 밖 `.audit/debate/20261116-spec005-plan.md`). 표결에 적은 토론 자리 이름은 가이드·실행·위험이고, A·B·C·D는 선택지 이름이다. 각 절의 "결정" 줄이 답이고, 선택지와 대가는 기록으로 남긴다.
- **R7 이후**는 spec과 앞 spec을 근거로 에이전트가 정했고 PR "가정"에 적는다.

## 지금 코드에서 확인한 사실

- `StoreBatch`(`Sources/MokaCore/Storage.swift:13-28`)가 유일한 여러 표 원자 쓰기이고 tasks·checkpoints·decisions_log만 담는다. `GRDBTaskRepository.apply`는 `db.write` 한 트랜잭션이다(`GRDBTaskRepository.swift:45-86`). 설정은 `SettingsStore`(`QuantumSettings.swift:1-4`)가 따로 쓴다. 앱은 두 저장소를 같은 `DatabaseQueue`로 만든다(`App/Sources/MokaApp.swift:132-141`).
- R-119: 앱 DB를 열지 못하면 `AppStorage(settings: InMemorySettingsStore(), repository: nil, ...)`(`App/Sources/AppState.swift:22-30`). 설정만 메모리로 대체되고 할 일 저장소는 없다.
- `decisions_log.user_action`과 `scheduler_choice`에는 DB CHECK가 없다(`schema/moka-schema.sql:3`). 읽을 때 열거형으로 막는다(`GRDBTaskRepository.swift:146`).
- `checkpoints.trigger`는 이미 `day_end`를 받지만 앱 코드에서 쓰는 곳이 없다(시험만).
- 도는 중 완료는 체크포인트를 남기지 않는다(`NotchSession.complete`, `NotchSession.swift:156`). 시간 끝에서 정상 종료하면 `lifecycleCheckpoint(.quit)`이 아무것도 남기지 않는다(도는 중만, `NotchSession.swift:222`).
- 시작(`NotchSession.start`)은 로그 줄을 남기지 않는다. 그래서 시작하고 버튼 없이 종료된 할 일은 체크포인트도 로그도 없을 수 있다.
- 시뮬레이터는 storage 모드에서 `InMemoryTaskRepository`를 쓰고, `activate`·`relaunch`가 `RecurrenceReset`·`LaunchRecovery` 뒤 고른다(`SimStorageRunner.swift:202-259`). 출력 키를 붙이는 조건은 spec 003에서 "그 이벤트가 시나리오에 있을 때"였다.
- `ValueTypeTests.swift:31-32`가 `SchedulerChoice.allCases`를 고정해, 값을 더하면 그 시험을 고쳐야 한다.

## Q1. 이월 표시와 판정 시각을 한 트랜잭션으로 쓰는 저장 경계 (spec R-412, SC-406)

- 결정: B. `TaskRepository`에 이월 판정 전용 읽기·쓰기 둘을 두고 `carry_judged_at`은 저장소만 다룬다. 경계 밖 저장소(`SettingsStore`)가 이 키를 쓰지 못하게 막는 시험을 둔다(data-model §9).
- 표결: 1라운드 3:0(B).

- 선택지:
  - A. `StoreBatch`에 설정 덮어쓰기 칸을 더한다. `apply` 한 번이 tasks와 settings를 같은 트랜잭션으로 쓴다. 쓴 시간, `last_start_day`도 버튼 커밋과 함께 쓸 수 있다.
  - B. `TaskRepository`에 이월 판정 전용 읽기·쓰기 둘을 더하고, 판정 시각 키는 저장소만 다룬다. `SettingsStore`와 `StoreBatch`는 그대로다.
  - C. 두 저장소를 묶는 작업 단위 프로토콜(`StoreTransaction`)을 MokaCore에 새로 두고 MokaStore가 같은 큐로 구현한다.
- 각 안의 대가:
  - A: settings 표를 쓰는 길이 둘(`SettingsStore`와 `apply`)이 된다. 메모리 구현은 두 저장소가 사전 하나를 함께 봐야 시험이 실제와 같다. `StoreBatch`가 커진다.
  - B: 바뀌는 곳이 가장 적다. 다만 쓴 시간처럼 다른 키도 버튼 커밋과 묶고 싶어지면 같은 무늬의 전용 메서드가 늘어난다.
  - C: 가장 일반적이다. 새 경계 하나와 앱·시뮬레이터 배선이 늘고, 단위 2가 커진다.
- 공통: R-119에서는 할 일 저장소가 없어 판정을 돌리지 않는다. 메모리 설정과 DB를 묶을 일이 생기지 않는다(data-model §9). 어느 안이든 `MokaCore`↔`MokaStore` 경계가 바뀌어 승인 항목 7이다.

## Q2. R-111이 되돌린 할 일을 같은 하루 안에서도 손댄 할 일로 세는 저장 표시 (spec Assumptions)

- 결정: A. 표시를 두지 않고 빈틈을 위험으로 적는다(plan 위험 14). D(시간 끝 화면 정상 종료에도 `notes: .empty`로 `quit` 체크포인트)는 다시 묻기 영향과 함께 별도 Issue(`ai-found`)로 넘긴다.
- 표결: 1라운드 3:0(A, 실행 자리는 D를 Issue로).

- 빈틈: 하루가 바뀐 뒤의 앱 시작은 R-111 → 판정 순서라 덮인다(spec 6d). 같은 하루 안에서 (1) 시간 끝 화면인 채 정상 종료하거나 (2) 도는 중·시간 끝에서 비정상 종료한 뒤 그날 다시 켜면, R-111이 되돌린 할 일은 체크포인트도 로그 줄도 없을 수 있어 다음 판정에서 손댄 할 일로 세지 못한다. (1)이 일상에서 생길 수 있는 경로라는 점이 spec 가정보다 넓다(위 사실).
- 선택지:
  - A. 표시를 두지 않는다. 빈틈을 위험으로 적는다. 그 할 일은 마감이 지났을 때만 카드에 오른다.
  - B. 설정 키 `carry_reverted`에 되돌린 할 일 ID를 쌓고, 판정 쓰기가 같은 트랜잭션에서 지운다(Q1 경계를 함께 씀). 스키마 변경 없음.
  - C. 되돌릴 때 그 할 일에 체크포인트 한 줄(계기 `quit`, 빈 두 줄, 경과 0분)을 남긴다. 저장 칸이 늘지 않지만 체크포인트 기록에 사람이 적지 않은 줄이 생기고, 판단 입력의 "최신 체크포인트"가 빈 줄로 바뀐다(spec 003 판단 입력 변화 → 다시 묻기).
  - D. 시간 끝 화면에서 정상 종료할 때도 `quit` 체크포인트를 남기게 spec 002 규칙을 넓힌다. 그때 적힌 두 줄이 남아 정보가 는다. 비정상 종료 빈틈은 남는다.

## Q4. 쓴 시간을 언제 무엇으로 세는가 (spec R-420, R-421, SC-405)

- 결정: B. 시작(과 "N분 더") 때 고른 분 × 60을 더하고, 도는 중 완료·미루기·바꾸기·종료 때 남은 초를 돌려준다(data-model §11). 비정상 종료하면 많이 세는 쪽으로 틀린다(plan 위험 15).
- 표결: 1라운드 2:1(B 실행·위험, 소수 A 가이드 "끝날 때 실제 초"). 사람 결정 2026-11-16 다수안.

- 선택지: A 작업 시간이 끝날 때 실제 초를 더함, B 시작할 때 고른 분을 더하고 일찍 끝나면 돌려줌, C 체크포인트·로그에서 셈(도는 중 완료 경과를 담을 새 저장 필요). data-model §11.
- 각 안의 대가:
  - A는 R-420 글자("타이머가 실제로 돈 시간")에 가장 가깝다. 비정상 종료한 작업 시간은 빠지고, 버튼 커밋과 같은 트랜잭션이 아니면 둘이 어긋날 수 있다(Q1과 맞물림).
  - B는 시작할 때 고른 칩만큼 먼저 세므로 시작하는 순간 쓴 시간이 가용 시간을 넘을 길이 없다. 처음 이 줄에 "B는 배정 합계를 그대로 센다"고 적었으나 틀려서 고쳤다(돌려주기 때문에 배정 합계와 쓴 시간이 다르다). 사람에게 물을 때는 두 안의 차이를 "평소엔 결과가 같고, 비정상 종료 때 B는 고른 분 전부를 세고 A는 0을 센다"로 설명했고, 사람은 그 설명으로 B를 골랐다(2026-11-16). 비정상 종료하면 고른 시간이 다 쓴 시간으로 남는다. 일찍 끝낼 때 돌려주는 계산이 하나 는다.
  - 리뷰 정정(PR #172): B는 돌려주기 때문에 "그날 시작한 작업 시간 분 합 ≤ 가용 시간"(처음 spec R-421·SC-405 글자)이 성립하지 않는다. 예: 2시간에서 60분 시작 → 10분에 완료(50분 돌려받음) → 110분 시작이면 시작한 분 합 170, 쓴 시간 120. 사람이 돌려주기를 골랐으므로 그 결과에 맞춰 spec R-420·R-421·SC-405와 불변식을 "쓴 시간(`used_s`) ≤ 가용 시간, 시작 칩 ≤ 남은 시간"으로 정정했다(사람 결정 2026-11-16(Q4-B)에 따른 정정).
  - C는 새 설정 값이 필요 없지만 도는 중 완료에 저장이 하나 늘어(스키마나 체크포인트 규칙 변경) 승인 항목이 는다.

## Q5. 가중 순환의 몫 셈 방식 (spec R-403, Assumptions "plan에서 정한다")

- 결정: A. 매끄러운 가중 순환. 창 정의를 함께 고친다: 창은 `order` 앞 셋을 먼저 정하고, 방금 할 일(`excluded`)과 연속 상한 후보는 그 고르기에서만 건너뛰며 몫은 버리지 않는다. 창에서 실제로 빠진 후보의 몫만 버린다. 몫은 정수로 키워 셈한다(data-model §5-4).
- 표결: 1라운드 2:1(A 가이드·위험, 소수 B 실행 "횟수 기반 + 창이 바뀌면 비움"). 창 정의 수정은 가이드·실행 두 자리가 지적해 함께 채택. 사람 결정 2026-11-16 다수안.
- 근거 시뮬레이션(메인 세션)은 특정 시나리오 하나다: 몫 5:3:2 창에서 0부터 10번 고른 뒤 급한 새 할 일이 1위(몫 5)로 드는 경우. 고친 창 규칙에서 두 방식 결과가 같았고, 5:3:2가 유지되며 그 새 1위가 바로 다음 차례에 뽑히고 이어지는 10번 중 5번 뽑혔다. "새 1위가 바로 다음 차례"는 일반 성질이 아니다(반례: 몫 상태 A 0, B 1200, C −1200에서 priority 2.0인 N이 들면 B가 먼저일 수 있음, data-model §5-4).
- 처음 초안의 창("`excluded`를 뺀 앞 셋")은 방금 할 일을 빼면 넷째 후보가 창에 들어와 US1-1 "D는 한 번도 뽑히지 않는다"를 어겼다.

- 선택지:
  - A. 매끄러운 가중 순환: 고를 때마다 창의 각 후보에 몫을 더하고, 가장 큰 후보를 고른 뒤 그 후보에서 몫 합을 뺀다. 5:3:2면 10번마다 정확히 5·3·2번이다.
  - B. 뒤처진 후보 먼저: 그 하루에 각 후보가 뽑힌 횟수와 목표 비의 차이가 가장 큰 후보를 고른다. 상태가 횟수뿐이라 읽기 쉽다.
  - C. 고정 표: 몫을 10칸 순서 표(예: A B A C A B A C A B)로 펼쳐 차례로 돈다. 창의 순서나 priority가 바뀌면 표를 다시 만든다.
- 공통 성질(data-model §5-4): 무작위 없음, 같은 입력이면 같은 결과, 100번에서 비 오차 2 이내(SC-401), 창 밖 0번, 동점은 순서 앞. 앱에서는 바꾸기·미루기 뒤 방금 할 일을 빼고(R-408), 미루기가 aging을 올려 창과 몫이 바뀌므로 어느 안이든 실제 비는 "가깝다"까지만 보장한다(spec US1-1).
- 갈리는 것: 창 구성이 바뀔 때(완료, 새 할 일, 판단 결과 변화) 남은 몫 상태를 어떻게 다루는지. A는 창을 떠난 후보의 몫을 버리고 새 후보는 0에서 시작한다. B는 횟수를 그 하루 동안 들고 있어 늦게 들어온 후보가 한동안 몰려 뽑힐 수 있다. C는 표를 처음부터 다시 돈다.

## R9. 워밍업의 "하루 첫 작업 시간" 판정 (R-406)

- 결정: 설정 키 `last_start_day`에 시작을 커밋한 하루를 쓴다. 그 값이 오늘이 아니면 워밍업이다.
- 이유: "앱을 다시 켜도 같은 판단"(R-406)에 저장이 필요하다. 체크포인트·로그는 시작에서 생기지 않는다(위 사실). 가용 시간 기록에 넣으면 R-119나 새 이벤트가 없는 시뮬레이터 시나리오(Q3-C)처럼 기록이 없는 경로에서 쓸 수 없다.
- 대안: 쓴 시간 > 0으로 판정(가용 시간 기록이 없는 경로에서 쓸 수 없음), 메모리(재시작에 깨짐).
- 쓰기 실패: 시작을 막지 않는다. 워밍업이 한 번 더 걸릴 뿐이다.

## R10. 하루 경계를 넘는 작업 시간의 쓴 시간

- 결정: 시작한 하루의 기록에만 더한다. 그 작업 시간이 하루 경계 뒤 시간 끝이 되어 누른 "N분 더"(spec 6c)도 처음 시작한 하루에 더한다. "N분 더"는 `last_start_day`를 바꾸지 않아 새 하루 첫 고르기는 워밍업이다. 그 "N분 더"의 칩과 끄기도 시작한 하루의 남은 분으로 정한다(메인 세션 가정, 재리뷰 지적 A의 안 (2)). 다른 안: (1) R-421을 같은 하루 안으로 좁혀 상한 없이 둠, (3) 어느 하루에도 넣지 않음. (2)는 R-421·SC-405를 하루마다 그대로 지킨다. 새 하루는 가용 시간 답을 쓸 때 0에서 시작한다.
- 이유: R-417 때문에 새 하루의 질문은 그 작업 시간이 끝난 뒤에야 뜨므로 경계 뒤 몫을 담을 기록이 없다. 나누려면 답 전 임시 값을 메모리에 들고 있어야 하고 재시작에 깨진다.
- 대안: 경계에서 나눔(정확하지만 임시 상태가 늘고 재시작에 잃음).

## R11. 오늘 끝과 겹친 시간 끝의 체크포인트 계기

- 결정: 그 화면의 완료·미루기·바꾸기 셋 모두 계기 `day_end`로 남긴다.
- 이유: R-422 "순서는 두 줄 입력(체크포인트 계기 `day_end`) → 오늘 끝"은 화면 전체의 순서를 말한다. "완료는 지금처럼 완료한다"는 상태 전이를 말하는 것으로 읽었다. 하루 끝 두 줄을 한 계기로 모으면 다음 날 재진입 조사에서 찾기 쉽다.
- 대안: 미루기·바꾸기만 `day_end`, 완료는 지금처럼 `quantum`(R-422의 "두 줄의 계기만 `day_end`다"를 미루기·바꾸기 문장으로만 읽음). 재작업 차이는 상수 하나라 가벼운 쪽(셋 다)으로 두고 PR "가정"에 적는다.

## R12. 로그 줄의 선택 규칙 이름을 들고 다니는 법 (R-411)

- 결정: `SchedulerMemory.pickedBy`에 노치 할 일을 띄운 규칙을 두고, 그 할 일의 버튼 줄에 쓴다. "다른 할 일"은 값을 바꾸지 않는다. 빠른 입력으로 넣어 곧바로 초안이 된 할 일은 앞 값, 없으면 `weighted_rotate_v1`이다.
- 이유: R-411 "바꾸기 전 초안에 쓰던 선택 규칙 이름을 그대로 쓴다". 빠른 입력의 초안(spec 002 R-103)은 spec이 말하지 않아 "직접 고르기만의 이름은 두지 않는다"를 따랐다.
- 대안: 빠른 입력 초안에 새 이름(승인 목록 밖이라 둘 수 없음).

## R13. 이월 카드 순서와 남은 개수

- 결정: 카드 순서는 `TaskListView.deadlineFirst`(지난 마감 → 가까운 마감 → 마감 없음, 동점은 id). 남은 개수는 지금 보이는 것을 포함한 수.
- 이유: 마감이 지난 일을 먼저 정하게 한다. "다른 할 일" 목록(spec 002 R-104)과 같은 순서라 사용자가 익숙하다. 남은 개수 글자는 시안 확정할 것 2번이다.
- 대안: priority 순(점수 없는 할 일이 섞이면 순서가 둘로 갈림), 만든 순.

## R14. 노치 모드 우선순위와 초안 비우기

- 결정: data-model §12 표. 카드·질문·오늘 끝이 되면 초안을 비운다.
- 이유: R-413("초안을 비우고 이월 카드"), R-419("답하기 전에는 할 일을 고르지 않는다"), R-422("노치 할 일이 없을 때 이미 닿아 있으면 바로 오늘 끝")를 한 표로 모았다. 도는 중·시간 끝은 끊지 않는다(R-417).
- 대안: 초안이 이월 대상이 아니면 그대로 둠(어제 초안이 오늘 질문 앞에 남아 R-419와 어긋남).

## R15. "다음" 표시 (R-434, spec 003 R-215 대체)

- 결정: 도는 중·시간 끝이면 상태를 바꾸지 않고 다음 고르기를 미리 돌린 결과(현재 할 일 뺌), 초안이면 그 할 일, 카드·질문·오늘 끝이면 없음.
- 이유: R-434 "스케줄러가 다음 고르기에서 고를 할 일에 붙인다". 지금은 도는 중일 때 1위였다(`NotchSession.swift:240`).
- 대안: 1위에 그대로(가중 순환과 어긋남).
- 남은 차이: 미루기는 aging을 올리고 완료는 창을 당기므로 미리 돌린 결과가 실제 다음 고르기와 다를 수 있다. Issue #174에서 다룬다.

## R16. 칩 상한과 막는 문구

- 결정: 남은 분보다 긴 프리셋은 꺼 두고, 직접 입력 오류에 `aboveRemaining`을 더한다. 문구는 확정 시안 글자.
- 이유: R-421 "고를 수 없다고 해요체로 알린다". 지금 직접 입력 오류(1분부터, 3시간까지)와 같은 자리를 쓴다(`QuantumChip.swift:70-72`).

## R17. 단위 나누기

- 결정: plan "작업 단위" 여섯. 순수 로직과 시뮬레이터(1), 스키마·저장·앱 고르기(2), 이월 카드 화면(3), 가용 시간과 오늘 끝(4), R-434 안내 글(5), 자동 시작과 "내일"(6, 밀리면 먼저 뺌).

## R18. 시작 전 화면에서 남은 시간보다 긴 작업 시간 (spec R-421, 사용자 결정 2026-11-16)

- 사용자 결정: 시작 전 화면에서 남은 시간보다 긴 작업 시간을 막지 말고 고를 수 있게 한다. "더 할래요"와 다른 기능이다.
- 결정(메인 세션 가정, PR "사람이 볼 결정"): 남은 분보다 긴 칩이나 직접 입력을 고르면 시작 버튼 자리에 "오늘 시간을 N분 늘려서 M분 할까요?" 확인 한 줄을 보인다. "늘리고 시작"이면 오늘 가용 시간을 모자란 분만큼 늘리고 그 칩으로 시작한다. "{남은 분}분만 할래요"면 칩을 되돌린다.
- 이유: (1) 늘린 만큼 가용 시간이 커지므로 `used_s ≤ 가용 시간` 불변식과 SC-405가 그대로다. (2) 사용자가 무엇이 바뀌는지(오늘 정한 시간) 보고 고른다. (3) 상한은 그대로라 늘린 시간을 다 쓰면 오늘 끝이 다시 와서 "오늘 시간 안에서만"이라는 FR-10 뜻이 남는다. (4) 확인 모양은 구체화 게이트(spec 004)와 같아 새 부품이 없다.
- 검토한 대안: 확인 없이 바로 늘림(실수로 긴 칩을 눌러도 오늘 시간이 조용히 커짐), 넘친 시간을 쓴 시간에 그냥 더함(불변식이 깨지고 오늘 끝 판정이 남은 분 음수를 다뤄야 함), 넘기면 그날 상한을 품("더 할래요"와 같아져 사용자 결정 "다른 기능"과 어긋남), 늘릴 분을 따로 고르게 함(칩 하나로 끝나던 시작이 두 단계가 됨).
- 시간 끝 화면: 늘리기를 두지 않는다. 시안 7·8번은 사람이 그대로 확정했고, 오늘 끝과 겹친 화면은 R-422 결정(debate 3:0, "N분 더"만 끔)을 지킨다. 그 뒤 "오늘 끝"의 "더 할래요"가 이어 가는 길이다. 하루 경계 뒤 "N분 더"(`budgetDay`)도 시간 끝 화면이라 늘리기가 없다.
- 행동 로그: 남기지 않는다. 가용 시간 답·"더 할래요"와 같은 규칙(R-416)이고, 늘린 양은 `day_budget.extended_min`에 남는다.

## R19. 가용 시간 직접 적기의 칸 (spec R-419, 사용자 결정 2026-11-16)

- 사용자 결정: 1·2·4·6·8시간 선택지에 더해 직접 시간을 적을 수 있게 한다.
- 결정(에이전트 가정, PR "가정"): 선택지 다섯 뒤 "직접…" 칸, 단위는 시간, 0.5 단위(30분), 0.5~16시간. 오류 문구 넷(data-model §11). 저장은 분(`day_budget.minutes`).
- 이유: 질문이 "몇 시간"이라 시간 단위가 자연스럽다. 30분 단위면 1.5·2.5처럼 흔한 값을 받고, 분 단위 오타(예: 2.3)를 막는다. 16시간은 깨어 있는 하루를 넘지 않게 잡은 위쪽 끝이다. 작업 시간 칩의 "직접…"(spec 001 R-004)과 같은 모양이라 익숙하다.
- 대안: 분 단위로 적기(질문 글과 단위가 다름), 시간·분 칸 둘(칸이 늘어 노치 폭에 빠듯함), 1시간 단위 정수만(1.5시간을 못 받음).
