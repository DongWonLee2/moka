# Feature Specification: 판단 공급자 고르기와 키 넣기

**Feature Branch**: `chore/spec-006-decision-providers`

**Created**: 2026-11-11

**Status**: Draft

**Input**: [ADR-0011](../../adr/ADR-0011-decision-providers.md)(판단 공급자 여러 개를 공통 코덱과 공급자 설정으로 지원한다, PR #116)을 구현한다. 사용자는 판단 공급자 다섯(Microsoft-Decision-1, TypeSafe Jev, Liquid d1-ultra, OpenAI Decisions, Perplexity Decider v1.2) 가운데 하나를 고르고 그 공급자의 키를 넣는다. 공급자 안의 모델은 사용자가 고르지 않고 앱이 정한다(사용자 결정 2026-11-11). Microsoft는 사용자가 Azure에 만든 배포의 주소와 배포 이름을 더 넣는다. 함께 담는 것은 spec 004 단위 4(온보딩 키 단계 R-313~R-315, 시안 9~11번, 설정 창 할 일 탭 키 확인 한 줄 R-317, 시안 15번)와 spec 003 R-213 기본 탭 키 칸을 공급자 고르기에 맞게 바꾸는 일이다.

기준: `origin/chore/adr-decision-providers`(`6d49080`)에 `origin/main`(`33cf800`, spec 004 단위 3 병합)을 병합한 `5d2b381`.

## 용어

spec 003·004 용어(판단 모델, 키, 판단 입력, 판단 결과, 쓰는 판단 결과, 보내기 장부, 키 확인 필요, 물을 수 있음)와 용어집(GLOSSARY.md)의 판단 공급자, 공급자 ID, 기준 모델 ID, 배포 이름을 그대로 쓴다. 이 spec에서 새로 쓰는 말은 다음과 같다.

- **고른 공급자**: 사용자가 고른 판단 공급자 하나. 설정 표에 공급자 ID로 남는다. 동시에 하나만 쓴다.
- **공급자 표**: 다섯 공급자의 공급자 ID, 화면 이름, 주소, 인증 방식, 요청 모양, 키 발급 링크를 담은 고정 값. 앱 코드에 있고 사용자가 바꾸지 않는다.
- **요청 모양**: 판단 공급자가 받는 요청과 돌려주는 응답의 꼴. System One 모양(TypeSafe, Microsoft, Liquid, Perplexity)과 OpenAI 모양 둘이다.
- **열린 공급자**: 사용자가 화면에서 고를 수 있는 공급자. 질문 파일에 기준 모델 ID가 있고, 사람이 첫 실제 호출을 확인한 공급자다(R-617).
- **잠정 임계값**: 라벨셋으로 검증하지 않은 기준 모델이 쓰는 임계값. 지금 Jev 값을 그대로 옮긴다(ADR-0011 결정 3).
- **보내는 곳**: 할 일 제목과 키가 실제로 가는 호스트 이름. 고른 공급자의 주소에서 꺼낸다.

## Goals

- 사용자가 다섯 공급자 가운데 열린 공급자 하나를 골라 그 키를 넣으면, 노치가 그 공급자의 판단 결과로 할 일을 고른다.
- 공급자를 바꿔도 다른 모델이 매긴 판단 결과가 순서에 섞이지 않는다.
- 사용자는 할 일 제목이 어느 호스트로 가는지 설정 창에서 안다.
- 지금 Jev 키를 쓰는 사용자는 업데이트 뒤 아무것도 하지 않아도 그대로 Jev로 판단 결과를 받는다.
- spec 004 단위 4(온보딩 키 단계, 할 일 탭 키 확인 한 줄)를 공급자 구조 위에서 마친다. 완료 조건은 PRD FR-21 수용 기준(키 없이 온보딩을 끝내도 노치에 할 일이 뜬다)이다.
- 스키마는 바꾸지 않는다(사용자 결정 2026-11-11).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 설정 창에서 공급자를 고르고 키를 넣는다 (Priority: P1)

사용자는 설정 창 기본 탭의 판단 모델 칸에서 공급자를 고른다. 칸에는 고른 공급자의 이름, 키 발급 링크, 할 일 제목이 가는 곳, 키 붙여 넣는 칸이 보인다. 사용자가 키를 저장하면 그 공급자로 할 일을 묻기 시작한다. 지금 Jev를 쓰던 사용자는 처음 열었을 때 이미 Jev가 골라져 있고 키가 저장되어 있다고 보인다.

**Why this priority**: ADR-0011을 사용자가 쓰는 첫 화면이다. 이 이야기 하나만 있어도 공급자 표, 요청 모양 둘, 공급자별 키가 모두 쓰인다.

**Independent Test**: 이름이 다른 가짜 공급자 둘과 가짜 키 보관함으로 고르기, 저장, 질의, 판단 결과 저장을 앱 시험으로 확인한다. 공급자마다 요청 본문은 MokaCore 단위 시험으로 확인한다. 칸 상태는 스냅샷으로 찍는다.

**Acceptance Scenarios**:

1. **Given** 업데이트 전부터 Jev 키가 저장되어 있고 공급자를 고른 적이 없다, **When** 업데이트한 앱을 켠다, **Then** 고른 공급자는 TypeSafe Jev이고, 키 칸은 저장되어 있다고 보이며, 키를 다시 넣지 않아도 판단 결과가 붙는다.
2. **Given** 기본 탭 판단 모델 칸을 연다, **When** 공급자 고르기를 펼친다, **Then** 다섯 공급자가 보이고 열린 공급자만 고를 수 있다. 열리지 않은 공급자는 왜 고를 수 없는지 해요체로 안내한다.
3. **Given** 열린 공급자 B를 골랐고 B의 키가 없다, **When** 칸을 본다, **Then** B의 화면 이름, B의 키 발급 링크(주소가 확인된 경우), 할 일 제목이 가는 곳(B 주소의 호스트), 붙여 넣는 칸, "저장"이 보인다.
4. **Given** B를 골랐다, **When** 키를 붙여 넣고 "저장"을 누른다, **Then** 키는 B의 키 보관함 항목에만 저장되고, 다시 물을 할 일을 B에 묻는다.
5. **Given** 고른 공급자의 기준 모델이 잠정 임계값을 쓴다, **When** 칸을 본다, **Then** 이 모델은 순서 기준값을 아직 맞추는 중이라는 안내가 보인다.
6. **Given** 키 확인 필요다(401·403), **When** 칸을 본다, **Then** spec 003 R-213 키 칸 여섯 상태가 고른 공급자 기준으로 그대로 보인다.

### User Story 2 - 공급자를 바꿔도 다른 모델 점수가 섞이지 않는다 (Priority: P1)

사용자가 Jev에서 다른 열린 공급자로 바꾸면, 앱은 Jev가 매긴 판단 결과를 순서에 쓰지 않고 모든 대기·진행 중 할 일을 새 공급자에 다시 묻는다. 다시 묻는 동안 노치는 마감이 가까운 순으로 돈다. 다시 Jev로 돌아오면 Jev 키는 남아 있어 다시 넣지 않아도 된다.

**Why this priority**: ADR-0011 평가 기준 3(점수가 섞이지 않음)이다. 이것이 없으면 공급자 고르기는 순서를 틀리게 만든다.

**Independent Test**: 이름이 다른 가짜 공급자 둘로 바꾸기 전후 쓰는 판단 결과와 다시 물을 할 일을 MokaCore 단위 시험과 앱 시험으로 확인한다. 바꾸기 직전에 떠난 질의의 답이 바꾼 뒤 도착하는 경우는 가짜 공급자의 붙잡기로 재현한다.

**Acceptance Scenarios**:

1. **Given** 할 일 셋에 공급자 A의 판단 결과가 있다, **When** 공급자를 B로 바꾼다, **Then** 쓰는 판단 결과가 비어 노치 후보는 마감일 순이 되고, 세 할 일 모두 다시 물을 할 일이 된다.
2. **Given** B로 바꾸었고 B의 키가 있다, **When** B의 답이 저장된다, **Then** 그 할 일부터 B의 판단 결과로 순서에 들어간다.
3. **Given** A로 보낸 질의가 아직 돌아오지 않았다, **When** 그사이 B로 바꾸고 A의 답이 도착한다, **Then** 그 답은 저장하지 않는다.
4. **Given** A에서 키 확인 필요였다, **When** B로 바꾼다, **Then** 키 확인 필요가 꺼지고 보내기 장부가 비며, 키가 있는지는 B의 항목으로 다시 읽는다.
5. **Given** B를 쓰다가 A로 돌아온다, **When** 칸을 본다, **Then** A의 키는 저장되어 있다고 보인다. A가 예전에 매긴 판단 결과는 질문 버전과 공급자가 같으면 다시 쓴다.
6. **Given** 공급자를 바꾼다, **When** 앱을 다시 켜지 않는다, **Then** 다음 질의부터 새 공급자로 간다.

### User Story 3 - Microsoft 배포를 쓴다 (Priority: P2)

Microsoft를 쓰는 사용자는 Azure에 만든 리소스 주소와 배포 이름을 넣고 키를 넣는다. 앱은 주소가 안전한지 먼저 보고, 어기면 이유를 안내하고 저장하지 않는다. 주소를 바꾸면 옛 키가 새 호스트로 가지 않도록 Microsoft 키를 지우고 다시 넣게 한다.

**Why this priority**: 사용자 결정의 다섯을 채우는 마지막 공급자다. 그러나 Microsoft 기준 모델 ID가 아직 정해지지 않아(ADR-0011 사람이 확인할 것) 열린 공급자가 되기 전까지는 사용자가 고를 수 없다.

**Independent Test**: 주소 허용 조건은 MokaCore 순수 함수 시험으로, 주소를 바꾸면 키를 지우는 것은 앱 시험(가짜 키 보관함)으로, 칸 상태는 스냅샷으로 확인한다. 리디렉트 거부는 사람이 loopback 로컬 서버로 확인한다.

**Acceptance Scenarios**:

1. **Given** Microsoft가 열린 공급자이고 골랐다, **When** 칸을 본다, **Then** 리소스 주소 칸, 배포 이름 칸, 키 칸이 보인다. 다른 공급자에는 주소 칸과 배포 이름 칸이 없다.
2. **Given** 주소 칸에 `http://example.invalid`(loopback 아님)를 넣었다, **When** 저장한다, **Then** 저장하지 않고 `https` 주소만 받는다고 안내한다.
3. **Given** 주소에 사용자 정보, 쿼리, 조각, 경로 가운데 하나가 있거나 호스트가 비었다, **When** 저장한다, **Then** 저장하지 않고 어떤 부분 때문인지 안내한다.
4. **Given** 주소가 `http://localhost:8080` 또는 `http://[::1]:8080`이다, **When** 저장한다, **Then** loopback이라 받는다.
5. **Given** Microsoft 키가 저장되어 있다, **When** 다른 리소스 주소로 바꿔 저장한다, **Then** Microsoft 키가 지워지고 키 칸은 키 없음으로 돌아가며 그 이유를 안내한다. 보내기 장부가 비고 키 확인 필요가 꺼진다.
6. **Given** 배포 이름을 바꿔 저장한다, **When** 다음 질의가 나간다, **Then** 요청의 모델 이름은 새 배포 이름이다. 보내기 장부가 비고 키 확인 필요가 꺼진다. 이미 저장된 Microsoft 판단 결과는 [NEEDS CLARIFICATION: 배포 이름(또는 주소)을 바꾸면 이미 저장된 Microsoft 판단 결과를 계속 쓰는가, 아니면 모든 대기·진행 중 할 일을 새로 묻고 그동안 쓰지 않는가?]
7. **Given** 주소를 넣었다, **When** 칸을 본다, **Then** 할 일 제목이 가는 곳으로 그 주소의 호스트 이름이 보인다.

### User Story 4 - 처음 켤 때 공급자를 고르고 키를 넣거나 건너뛴다 (Priority: P2)

처음 앱을 켠 사용자는 온보딩 첫 단계에서 판단 모델 키를 넣는다. 공급자를 고르고, 그 공급자의 발급 링크로 키를 받아 붙여 넣는다. 키가 없으면 건너뛰고, 노치는 마감이 가까운 순으로 할 일을 띄운다. spec 004 R-313~R-315를 공급자 구조에 맞게 바꾼 것이다.

**Why this priority**: PRD FR-16·FR-21(P0)이지만 새 사용자 첫 실행에만 보인다. 이미 온보딩을 끝낸 사용자는 설정 창 기본 탭에서 넣는다(spec 004 위험 1, 위험 6).

**Independent Test**: 가짜 설정 저장소(온보딩 안 끝남)와 가짜 키 보관함으로 키 단계의 고르기, 저장, 건너뛰기, 실패를 앱 시험으로 확인하고 상태를 스냅샷으로 찍는다. 새 사용자 첫 실행은 사람이 macOS 새 사용자 계정에서 본다.

**Acceptance Scenarios**:

1. **Given** 온보딩을 끝내지 않았고 키가 없다, **When** 앱을 처음 켠다, **Then** 첫 단계가 키 단계이고 세 단계 가운데 첫째로 보인다. 키 단계에는 [NEEDS CLARIFICATION: 온보딩 키 단계에서 공급자를 고르게 하는가? 고르게 하면 Microsoft의 주소·배포 이름 칸도 온보딩에 두는가?] 기준으로 정한 공급자의 발급 안내 한 줄, 발급 링크, 붙여 넣는 칸, "건너뛰기", "다음"이 보인다.
2. **Given** 키 단계에서 칸에 키를 붙여 넣었다, **When** "다음"을 누른다, **Then** 키가 그 공급자의 키 보관함 항목에 저장되고 고른 공급자가 설정 표에 남으며 일정 단계로 넘어간다. 키 값은 다시 보이지 않는다.
3. **Given** 칸이 비어 있다, **When** 키 단계를 본다, **Then** "다음"은 꺼져 있고 "건너뛰기"는 켜져 있다.
4. **Given** "건너뛰기"를 눌렀다, **When** 나머지 두 단계를 끝내고 할 일을 넣는다, **Then** 노치에 마감일 순으로 할 일이 뜬다.
5. **Given** 키 저장이 실패한다, **When** "다음"을 누른다, **Then** 키 단계에 머물고 다시 해 달라는 문구가 보이며 "건너뛰기"는 그대로 켜져 있다.
6. **Given** 키를 저장한 뒤 온보딩을 끝내지 않고 앱을 껐다, **When** 다시 켠다, **Then** 온보딩이 처음부터 보이고, 키 단계는 그 공급자의 키가 저장되어 있다고 보이며 "다음"으로 넘어갈 수 있다.
7. **Given** 온보딩을 이미 끝냈다, **When** 앱을 켠다, **Then** 온보딩은 보이지 않는다(spec 002 R-116).

### User Story 5 - 키가 맞지 않으면 할 일 탭에서도 알 수 있다 (Priority: P3)

키 확인 필요인 동안 설정 창 할 일 탭 목록 위에 한 줄이 보이고, 누르면 같은 창의 기본 탭으로 바뀐다. 노치 펼친 화면의 같은 표시는 spec 004 단위 3에서 이미 들어갔다. 이 이야기는 시안 15번(사용자 확정 2026-11-10)을 그대로 만든다.

**Why this priority**: spec 004 R-317이 공급자 구조를 기다리며 미뤄졌다. 문구가 공급자와 상관없어 바꿀 것이 거의 없다.

**Independent Test**: 가짜 공급자가 401을 내게 해 키 확인 필요를 만들고 할 일 탭을 스냅샷으로 찍는다. 키를 다시 저장하거나, 지우거나, 공급자를 바꾸면 표시가 사라지는지 앱 시험으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 키 확인 필요다, **When** 할 일 탭을 연다, **Then** 목록 위에 "키가 맞지 않아 새 할 일은 판단 모델에 묻지 못하고 있어요."와 "기본 탭에서 확인"이 보인다.
2. **Given** 그 줄이 보인다, **When** "기본 탭에서 확인"을 누른다, **Then** 같은 창이 기본 탭으로 바뀐다.
3. **Given** 키 확인 필요다, **When** 키를 다시 저장하거나, 지우거나, 공급자를 바꾼다, **Then** 할 일 탭과 노치의 표시가 함께 사라진다.
4. **Given** 키가 없다, **When** 할 일 탭을 본다, **Then** 표시가 없다.

---

### Edge Cases

- **고른 공급자가 질문 파일에 없음:** 설정 표에 남은 공급자 ID가 질문 파일 기준 모델 표에 없으면 판단 기능을 끈다. 노치는 마감일 순으로 돌고, 질의를 보내지 않으며, 로그 한 줄을 남긴다. 앱은 멈추지 않는다(ADR-0011 결정 3).
- **기준 모델의 임계값이 없음:** 읽기 규칙 2를 어긴 질문 파일은 읽지 않고 판단 기능을 끈다. 임계값을 읽는 곳은 값이 없을 때 게이트를 열지 않는다.
- **설정 표에 모르는 공급자 ID:** 공급자 표에 없는 값이면 고른 공급자가 없다고 보고 판단 기능을 끈다. 기본 탭은 공급자를 다시 골라 달라고 안내한다.
- **고른 공급자가 열리지 않은 공급자:** 다음 버전에서 열린 공급자 목록이 줄어 남은 값이 열리지 않은 공급자이면, 위와 같이 판단 기능을 끄고 다시 골라 달라고 안내한다. 키는 지우지 않는다.
- **같은 공급자를 다시 고름:** 아무것도 바꾸지 않는다. 장부도 비우지 않는다.
- **공급자를 바꾸는 중 키 확인 필요의 질의가 떠 있음:** 바꾼 뒤 도착한 이전 공급자 답은 401이어도 키 확인 필요를 켜지 않는다.
- **공급자를 바꾼 직후 게이트가 열려 있음:** 게이트 판정은 쓰는 판단 결과로 하므로, 새 공급자의 판단 결과가 없으면 게이트가 닫힌다(spec 004 R-306 "물을 수 있음"과 쓰는 판단 결과 없음).
- **질문 파일 v1에서 v2로 올림:** 질문 버전이 달라져 기존 판단 결과는 Jev를 계속 써도 모두 다시 묻는다. 그동안 노치는 마감일 순으로 돈다(ADR-0011 결정 6 트레이드오프).
- **Microsoft 주소 앞뒤 공백·줄바꿈:** 저장 전에 지운다. 지우고 비면 저장을 끈다.
- **Microsoft 주소 끝의 `/` 하나:** 경로가 없는 것으로 본다(가정, 아래 Assumptions).
- **대소문자가 다른 loopback:** `LOCALHOST`도 loopback으로 본다. 호스트 비교는 대소문자를 가리지 않는다.
- **리디렉트 응답:** 3xx를 따라가지 않고 서버 오류로 본다. 두 번째 요청을 보내지 않는다.
- **공급자가 문서에 없는 상태 코드를 돌려줌:** 서버 오류로 보고 그 할 일 실패로 기록한다(spec 003 R-211).
- **OpenAI 응답에 score 값이나 신뢰도 칸이 없음:** 해석 실패로 보고 판단 결과를 저장하지 않는다. 확률로 계산할지는 첫 실제 호출 뒤 정한다(ADR-0011 결정 1).
- **Keychain에 이전 공급자 키가 남음:** 지우지 않는다. 사용자가 그 공급자를 다시 골라 "지우기"를 누르면 지운다.
- **온보딩, Keychain을 읽지 못함:** 키 없음으로 보고 붙여 넣는 칸을 보인다(spec 004 Edge Cases).
- **할 일 탭 키 확인, 앱을 다시 켬:** 키 확인 필요는 메모리 값이라 사라진다. 다음 질의가 다시 401이면 다시 보인다.

| R-623 | Microsoft를 고르면 리소스 주소 칸과 배포 이름 칸을 보인다. 다른 공급자에는 두 칸이 없다. 주소가 R-605를 어기면 저장하지 않고 어긴 이유를 해요체로 안내한다. 두 칸 앞뒤 공백·줄바꿈은 지우고 비면 저장을 끈다. 주소를 바꾸면 키를 지운다는 사실을 저장 전에 칸 옆에 안내하고, 저장 뒤 키 칸은 키 없음으로 돌아간다 | ADR-0011 결정 2 |
| R-624 | 온보딩은 키, 일정, 기본값 세 단계다. 키 단계는 공급자의 발급 안내 한 줄, 그 공급자의 발급 링크, 가림 입력 칸, "건너뛰기", "다음"을 보인다. 칸이 비면 "다음"을 끈다. 공급자를 키 단계에서 고르는지와 Microsoft 칸을 두는지는 US4 시나리오 1의 확인 질문대로 한다. spec 004 R-313을 대체한다 | spec 004 R-313, PRD FR-21(1)·FR-16 |
| R-625 | 키 단계의 "다음"은 설정 창 키 저장과 같은 동작(앞뒤 공백·줄바꿈 지움, 그 공급자 항목에만 저장, 보내기 장부 비움, 저장할 때 시험 호출 없음)을 하고, 고른 공급자를 설정 표에 남긴 뒤 다음 단계로 간다. 저장이 실패하면 키 단계에 머물러 다시 해 달라는 문구를 보이고 "건너뛰기"는 켜 둔다. 그 공급자 키가 이미 있으면 붙여 넣는 칸 대신 저장되어 있다고 보이고 "다음"을 켠다. spec 004 R-314를 대체한다 | spec 004 R-314 |
| R-626 | 키 단계를 건너뛰고 온보딩을 끝내도 노치는 할 일을 마감일 순으로 띄운다. 온보딩 끝냄 표시와 다시 보이지 않음은 spec 002 R-116 그대로다. 키 저장은 온보딩 끝냄과 따로 일어나 끝내기 전에 앱을 꺼도 남는다. spec 004 R-315 그대로다 | spec 004 R-315, PRD FR-21 수용 기준 |
| R-627 | 키 확인 필요인 동안 설정 창 할 일 탭은 목록 위에 "키가 맞지 않아 새 할 일은 판단 모델에 묻지 못하고 있어요."와 "기본 탭에서 확인"을 보인다(시안 15번, 사용자 확정 2026-11-10). 누르면 같은 창을 기본 탭으로 바꾼다. 켜지고 꺼지는 때는 spec 004 R-318 그대로이고, 공급자를 바꿀 때도 꺼진다. spec 004 R-317을 이 spec에서 만든다 | spec 004 R-317·R-318 |

### Key Entities

- **공급자 표**: 다섯 줄. 공급자 ID, 화면 이름, 주소 규칙, 인증 방식, 요청 모양, 발급 링크(확인 여부 포함), 첫 실제 호출 확인 여부. 코드의 고정 값이고 저장하지 않는다.
- **고른 공급자 설정**: 설정 표의 고른 공급자 ID, Microsoft 리소스 주소, Microsoft 배포 이름. 키 이름은 plan에서 `CoreSettings` 무늬로 정한다. 스키마는 그대로다.
- **키 보관함 항목**: 공급자마다 하나. account가 공급자 ID다.
- **질문 파일 v2**: v1 질문 그대로, `models`(공급자 ID에서 기준 모델 ID로), `provisional`, 기준 모델 ID 키 임계값. 공개 계약이다.
- **판단 결과**: spec 003 `scores` 한 줄 그대로. 공급자 칸으로 공급자를 비교한다.
- **주소 검사 결과**: 받음, 또는 거부 이유(스킴, 빈 호스트, 사용자 정보, 쿼리, 조각, 경로). 저장하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-601**: 지금 TypeSafe 요청·응답·상태 코드 시험이 이름만 바꿔 전부 PASS이고, System One 공급자 넷의 요청 본문은 보낼 모델 이름만 다르다(MokaCore 단위 시험).
- **SC-602**: 공식 문서 예시 모양의 가짜 OpenAI 응답이 같은 판단 응답으로 바뀌고, 칸이 빠지거나 범위 밖인 가짜 응답은 해석 실패가 된다(MokaCore 단위 시험).
- **SC-603**: 주소 검사 사례 표(받음: `https` 호스트, `http://localhost`, `http://127.0.0.1`, `http://[::1]`, 대문자 `LOCALHOST`. 거부: loopback 아닌 `http`, 빈 호스트, 사용자 정보, 쿼리, 조각, Microsoft 주소의 경로)가 모두 기대대로이고 거부 이유 종류가 맞다(MokaCore 단위 시험).
- **SC-604**: 읽기 규칙 2를 어긴 질문 파일은 읽지 않아 판단 기능이 꺼지고, 같은 `version`의 값을 바꾼 파일은 고정값 시험이 실패한다(MokaCore 단위 시험, pytest).
- **SC-605**: 이름이 다른 가짜 공급자 둘로 바꾸면 쓰는 판단 결과가 비고 모든 대기·진행 중 할 일이 다시 물을 할 일이 되며, 바꾸기 전에 떠난 질의의 답은 저장되지 않는다(MokaCore 단위 시험과 앱 시험).
- **SC-606**: 고른 공급자가 질문 파일에 없거나 기준 모델 임계값이 없을 때 앱은 멈추지 않고, 노치는 마감일 순으로 돌며, 질의는 0건이다(앱 시험).
- **SC-607**: 업데이트 전 Jev 키를 가진 사용자는 업데이트 뒤 조작 0번으로 판단 결과를 받는다(기존 account `typesafe`를 넣은 가짜 키 보관함으로 앱 시험, 사람이 확인용 빌드에서 한 번 확인).
- **SC-608**: 저장한 키는 고른 공급자의 키 보관함 항목에만 있고 설정·앱 DB·로그에 없다. 공급자를 바꿔도 이전 공급자 키는 남는다(spec 003 SC-208과 같은 시험을 공급자 둘로).
- **SC-609**: Microsoft 주소를 바꿔 저장하면 Microsoft 키가 지워지고 키 칸이 키 없음이 된다(앱 시험).
- **SC-610**: 사용자는 설정 창 기본 탭 한 화면에서 공급자 고르기, 키 붙여 넣기, 저장까지 조작 세 번으로 마친다(Microsoft는 두 칸을 더해 다섯 번). 보내는 곳 호스트가 같은 화면에 보인다(스냅샷).
- **SC-611**: 키 없이 온보딩 세 단계를 끝내는 데 조작이 세 번(건너뛰기, 건너뛰기, 시작하기)이고, 끝낸 뒤 할 일을 넣으면 노치에 뜬다(앱 시험, 사람이 새 사용자 계정에서 한 번 확인). spec 004 SC-307 그대로다.
- **SC-612**: 키 확인 필요가 켜지면 할 일 탭에 표시가 보이고, 키를 저장하거나, 지우거나, 공급자를 바꾸면 노치와 할 일 탭 모두에서 사라진다(앱 시험과 스냅샷).
- **SC-613**: 시험·CI는 실제 판단 API를 한 번도 부르지 않고 실제 Keychain과 앱 DB를 열지 않는다. 기존 spec 001~004 시험과 `moka-sim` 기대 출력은 바뀌지 않는다. `schema/moka-schema.sql`과 스키마 계약 pytest는 바뀌지 않는다.
- **SC-614**: 사람이 loopback 로컬 서버로 리디렉트를 돌려줄 때 실패 종류가 서버 오류이고 두 번째 요청이 없다(사람 확인, PASS/FAIL).
- **SC-615**: 열린 공급자를 하나 늘릴 때마다 사람이 자기 키로 첫 실제 호출을 하고 PASS/FAIL과 필드 이름만 기록한다(사람 확인).

## Assumptions

- 사용자는 작성자 1인, macOS 14 이상이다. 동시에 쓰는 공급자는 하나다.
- ADR-0011은 Proposed이고 PR #116 병합으로 확정된다. 이 spec은 ADR이 확정된 뒤 plan으로 간다. ADR 결정을 바꾸려면 새 ADR을 debate로 제안한다.
- 키 발급 링크는 조사 요약(2026-11-10) 기준이다. 확인되지 않은 주소는 사람이 공식 문서에서 확인하기 전에는 화면에 링크로 보이지 않는다(R-620).

  | 공급자 | 발급 링크 | 상태 |
  |---|---|---|
  | TypeSafe Jev | 문서에 없음 | 미확인(ADR-0011 사람이 확인할 것) |
  | Microsoft-Decision-1 | 조사 요약에 없음(Azure 구독과 배포 필요) | 미확인 |
  | Liquid d1-ultra | `console.liquid.ai` | 조사 요약 기준 |
  | Perplexity Decider v1.2 | `console.perplexity.ai` | 조사 요약 기준 |
  | OpenAI Decisions | `platform.openai.com/api-keys` | 미확인(조사 요약 표시) |

- 기존 사용자는 설정 표에 고른 공급자가 없으므로 TypeSafe Jev로 본다(R-614). 그래서 기존 Jev 키를 다시 넣지 않는다.
- 공급자를 바꿔도 이전 공급자 키는 Keychain에 남긴다. account가 공급자마다 따로라 지울 이유가 없고, 다시 돌아올 때 다시 넣지 않아도 된다. 지우기는 그 공급자를 고른 상태의 "지우기"로만 한다.
- 이전 공급자로 돌아오면 그 공급자가 예전에 매긴 판단 결과를 다시 쓴다(R-611 비교가 질문 버전과 공급자뿐이므로). 할 일마다 판단 결과는 한 벌이라 바꾼 뒤 새 공급자가 덮어쓴 할 일은 다시 묻는다.
- 보내는 곳은 Microsoft만이 아니라 다섯 공급자 모두에 보인다. ADR-0011 평가 기준 5(할 일 제목이 가는 곳을 사용자가 앎)를 고정 주소 공급자에도 적용한 해석이다.
- Microsoft 주소 끝의 `/` 하나는 경로가 아닌 것으로 본다. 그 밖의 경로는 거부한다(ADR-0011 결정 2 가정 "넣은 주소에 경로가 있으면 거부"의 경계값).
- Microsoft 인증은 `api-key` 헤더만 쓴다(ADR-0011 가정). Entra 토큰은 받지 않는다.
- 거부한 3xx는 서버 오류다(ADR-0011 가정).
- 잠정 임계값은 지금 Jev 값(`concrete 0.5`, `avoiding 0.7`)을 옮긴다(ADR-0011 가정). 값이 바뀌면 PR "사람이 볼 결정"에 이전 값과 새 값을 적는다.
- 질문 파일 v2 제안의 `models`에 Microsoft 줄은 기준 모델 ID가 정해질 때까지 넣지 않는다. 그동안 Microsoft는 열린 공급자가 아니다.
- 질문 파일을 v2로 올리면 기존 판단 결과는 모두 다시 묻는다. ADR-0011이 입력 비용(100만 토큰에 0.01~0.10달러, 출력 무료)과 할 일 규모(수십 건)로 받아들인 비용이다.
- 공급자를 바꾸면 질문 버전이 같아도 다시 묻는다. 바꾸기 전에 확인 창을 띄우지 않는 이유는 되돌리면 이전 판단 결과가 다시 쓰여 손해가 작기 때문이다(R-622).
- 앱 상태가 바꾼 공급자를 다시 켜지 않고 쓰려면, 판단 설정이 공급자 하나 대신 공급자를 만드는 방법을 들어야 한다. 이것은 앱 안쪽 모양이고 공개 계약(`DecisionProvider`)은 바꾸지 않는다. 모양은 plan에서 정한다.
- 화면 문구는 고객용 해요체이고, 막을 때는 이유를 안내한다. 공급자 고르기, Microsoft 칸, 잠정값 안내, 온보딩 키 단계의 문구와 자리는 새 HTML 시안을 사람이 확정한 뒤 만든다. 시안 9~11번은 TypeSafe 문구로 확정되어 있고, 6번(키 단계 문구와 링크)은 공급자 구조 뒤로 보류되어 있다. 시안 15번 문구는 공급자와 상관없어 그대로 쓴다.
- 기본 탭 칸 제목 "판단 모델 키 (TypeSafe)"(spec 003 확정 문구)는 고른 공급자 이름을 따르게 바뀐다. 그래서 spec 003 키 칸 스냅샷 참조 이미지가 바뀔 수 있고, 바뀌면 PR에 이유를 적는다.
- OpenAI score 답의 칸 이름, Microsoft 응답 `model` 칸, Liquid 고정 버전 규칙은 미확인이다(ADR-0011 미확인). 해당 공급자는 확인 전 열리지 않으므로 이 spec의 사용자 경험에는 영향이 없다.

| 의존성·CI | 변경 없음 | ADR에 없음 |

이 spec이 ADR-0011 밖에서 더한 승인 후보는 없다. R-615의 "바꾼 뒤 도착한 답을 저장하지 않음"은 앱 안쪽 규칙이고 공개 계약을 바꾸지 않는다.

## Non-Goals

- 오픈웨이트(사용자가 띄운 서버) 주소와 요청 모양 고르기. 주소 허용 조건(R-605)만 지킨다.
- 공급자 안에서 기준 모델 고르기(사용자 결정 2026-11-11). 생기면 ADR-0011 결정 6을 대안 A(새 열)로 다시 본다.
- 중계 서비스, 여러 공급자 차례로 시도, 공급자 둘 이상 동시 사용.
- 저장할 때 키 시험 호출, 키 값 다시 보기.
- Entra 토큰 인증.
- 잠정 임계값 모델의 라벨셋 검증(사람이 한다).
- 마일스톤 4·5(스케줄러, 서킷브레이커, 429 백오프 등).
- 이미 온보딩을 끝낸 사용자에게 키 단계를 다시 보이기.

## 단위 나누기 제안

| 단위 | 담는 것 | 승인·선행 |
|---|---|---|
| 1 | MokaCore 코덱과 공급자 표: R-601~R-606, contracts/decision-provider.md | 승인 항목 1. ADR-0011 병합 뒤 |
| 2 | 질문 파일 v2와 판단 결과 규칙: R-607~R-612, contracts/questions-json.md, pytest 계약 | 승인 항목 2. 단위 1과 병렬 가능(고치는 파일이 다름) |
| 3 | 앱 공급자 설정과 키: R-613~R-619, R-629의 리디렉트 사람 확인 | 단위 1·2 뒤 |
| 4 | 설정 창 화면: R-620~R-623, R-627 | 새 시안 확정과 단위 3 뒤 |
| 5 | 온보딩 키 단계: R-624~R-626 | 새 시안 확정, 확인 질문 2 답, 단위 3 뒤. 단위 4와 병렬 가능 |

R-628은 모든 단위의 공통 조건이고, R-630 대체 표기는 단위 1과 2에서 그 단위가 바꾸는 문서에 붙인다. 열린 공급자를 늘리는 일(R-617, R-629 첫 실제 호출)은 공급자마다 따로 작은 PR이다. 밀리면 단위 5를 먼저 다음 spec으로 넘긴다(spec 004 위험 1과 같은 순서).

## 대안과 위험

대안(고른 안과 기각한 안, 에이전트 초안이며 사람 확인 전):

| 결정 | 기각한 안(한 줄 이유) | 근거 |
|---|---|---|
| 열리지 않은 공급자도 목록에 보이되 고를 수 없음 | 목록에서 숨김(다섯을 지원한다는 사용자 결정이 화면에서 보이지 않음) | ADR-0011 결정 1 가정 |
| 이전 공급자 키를 남김 | 바꿀 때 지움(돌아오면 다시 넣어야 함, account가 따로라 섞일 일이 없음) | ADR-0011 결정 5 |
| 보내는 곳을 다섯 공급자 모두 보임 | Microsoft만(고정 주소 공급자도 제목이 외부로 감) | ADR-0011 평가 기준 5 |
| 공급자 바꾸기에 확인 창 없음 | 확인 창(되돌리면 이전 판단 결과를 다시 써 손해가 작음) | ADR-0011 결정 6 |

위험:

- 위험 1(열린 공급자 하나): Microsoft 기준 모델 ID와 넷의 첫 실제 호출이 확인되기 전에는 사용자가 실제로 고를 수 있는 공급자가 Jev 하나다. 사용자가 이 spec 뒤에 바로 다섯을 쓰리라 기대하면 어긋난다. 확인 질문 1의 답이 이 위험의 크기를 정한다.
- 위험 2(질문 파일 v2 비용): v2로 올리는 순간 모든 할 일을 다시 묻는다. 그동안 노치는 마감일 순이다.
- 위험 3(배포 이름 빈틈): 같은 배포 이름이 가리키는 모델이나 가중치가 바뀌면 공급자 비교로 잡지 못한다(ADR-0011 남는 빈틈). 확인 질문 3은 사용자가 배포 이름을 바꾼 경우만 다룬다.
- 위험 4(시안): 시안 9~11번은 TypeSafe 문구로 확정되어 있어 새 시안이 필요하다. 시안 확정이 늦으면 단위 4·5가 늦는다.
- 위험 5(개인정보): 공급자를 바꾸면 모든 할 일의 판단 입력(제목 포함)이 새 공급자에게 간다. 보내는 곳 표시(R-606·R-620)로 사용자가 안다.
- 위험 6(사람 확인): 리디렉트 거부와 공급자별 첫 실제 호출, 온보딩 새 사용자 첫 실행은 사람만 확인할 수 있다.
