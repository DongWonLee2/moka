# Feature Specification: 판단 모델 연동 MVP (마일스톤 3)

**Feature Branch**: `chore/spec-003-decision-model`

**Created**: 2026-11-06

**Status**: Draft

**Input**: PRD(`~/Dev/ai-platform/projects/moka/prd.md`, 저장소 밖) 12장 마일스톤 3 "판단 모델 연동" — FR-03(판단 질의), FR-04(점수 산출), FR-14(어댑터), FR-16 일부(설정 창 API 키). [spec 002](../002-storage-checkpoint/spec.md)(저장과 체크포인트) 위에 쌓는다.

결정 이력(질문별 결정과 기각한 안은 [research.md](research.md)):
- 범위와 규칙은 2026-11-06 요구 다지기에서 정했다. 질문마다 토론(가이드·실행·위험 세 자리)으로 추천안을 만들고 사용자가 하나씩 골랐다.
- 사용자가 토론 안과 다르게 정한 것:
  - 판단 질문 blocked를 없앴다(research R2).
  - impact 옵션과 판단 입력의 일정 중요도를 화면 말 "조금/꽤/아주"로 맞췄다(R2).
  - 질의가 실패한 할 일은 다음 활성화 때 한 번 다시 묻고, 401 뒤에는 키를 다시 저장할 때까지 묻지 않는다(R17).
- EGM 설계 리뷰(2026-11-07) 뒤 사용자가 바꾼 것: 질의 시점을 트리거 표에서 "입력이 바뀌면 다시 묻기" 한 규칙으로(R17), 키가 없을 때도 마감일 순(R17).
- 다음 spec(v1 태그 2026-11-09 전)으로 넘긴 것은 Non-Goals에 있다.

## 용어

- **판단 모델**: 텍스트를 만들지 않고 정해진 질문에 확률만 돌려주는 외부 모델. 이번에 쓰는 것은 TypeSafe(판단 모델 공급 회사)의 Jev 모델이고, 중개 서비스(OpenRouter) 없이 TypeSafe API를 바로 부른다.
- **키**: TypeSafe API 키. 사용자가 설정 창에 넣는다.
- **판단 입력**: 판단 모델에 보내는 내용. 오늘 날짜, 할 일 한 건, 일정 목록, 그 할 일의 마지막 체크포인트(R-201).
- **판단 결과**: 판단 모델이 돌려준 질문별 확률을 할 일마다 저장한 것(R-205). "점수 있는 할 일"은 쓸 수 있는 판단 결과가 있는 할 일이다.
- **priority**: 판단 결과와 미룬 횟수로 고를 때마다 계산하는 값(R-204). 저장하지 않는다.
- **활성화**: [spec 002](../002-storage-checkpoint/spec.md) R-113의 앱 시작·깨어남·노치 펼침·설정 창 열기.
- **noul·score**: TypeSafe 판단 질문의 두 타입. noul은 "이 문장이 참일 확률" 하나를, score는 낮음→높음 옵션 가운데 어디인지(옵션 번호의 확률 가중 평균)를 돌려준다.
- **초안**: 타이머를 시작하기 전 노치에 떠 있는 할 일(시작 전 화면). **실행 중**: 타이머가 도는 할 일.
- **정준 바이트**: 같은 판단 입력이면 언제나 같은 바이트가 나오도록 키 순서·이스케이프를 고정해 만든 JSON. 해시를 여기서 만든다.
- **보내기 장부**: 같은 판단 입력으로 이미 보낸 질의를 다시 보내지 않으려고 앱이 메모리에만 두는 기록(R-207).
- **golden**: 시뮬레이터 시험이 비교하는 기대 출력 파일.

## Goals

- 완료 조건(PRD 12장): 모델 점수로 정렬된 할 일이 노치에 뜬다.
- 할 일을 저장하면 판단 모델이 판단 입력만 보고 확률을 돌려주고, 코드가 판단 결과를 저장한 뒤 priority로 노치 순서를 정한다.
- 키가 없거나 판단 모델이 실패해도 표시·타이머·버튼은 그대로 동작하고, 노치는 마감일 순으로 할 일을 고른다.
- 사람이 설정 창에서 priority 순서를 눈으로 확인할 수 있고, 화면 없이 시험으로 규칙을 확인한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 키를 넣으면 노치가 priority 순으로 할 일을 띄운다 (Priority: P1)

사용자는 설정 창 기본 탭에 키를 붙여 넣고 저장한다. 할 일을 저장하면 몇 초 안에 판단 결과가 붙고, 노치는 priority가 높은 할 일부터 고른다. 설정 창 할 일 목록에서 줄마다 priority 숫자를 볼 수 있다.

**Why this priority**: 마일스톤 3 완료 조건이다.

**Independent Test**: 가짜 판단 공급자로 할 일 셋에 서로 다른 확률을 주고, 노치에 priority 1위가 뜨는지, 바꾸기 뒤 2위가 뜨는지, 설정 창 줄마다 priority가 보이는지 확인한다. 실제 키로는 사람이 확인용 빌드에서 한 번 확인한다.

**Acceptance Scenarios**:

1. **Given** 키가 저장되어 있다, **When** 설정 창 할 일 탭이나 노치 빠른 입력으로 "가짜 할 일 A"를 저장한다, **Then** 10초 안에 A에 판단 결과가 붙고 설정 창 A 줄에 priority 숫자가 보인다.
2. **Given** 점수 있는 대기 할 일 A(priority 1.2)·B(0.9)·C(1.5)가 있고 실행 중인 타이머가 없다, **When** 노치를 본다, **Then** C가 시작 전 화면으로 뜬다.
3. **Given** 노치에 C가 떠 있다, **When** C를 시작해 바꾸기를 누르고 두 줄을 마친다, **Then** 노치는 다음 순위 A를 고른다. A 뒤에 바꾸기를 하면 B, B 뒤에는 처음(C)으로 돌아간다.
4. **Given** A(1.2)·B(0.9)·C(1.5)이고 노치에 A가 떠 있다(C 뒤 바꾸기), **When** A를 시작해 미루기를 누르고 두 줄을 마친다, **Then** A의 미룬 횟수가 1 올라 priority가 다시 계산되고(R-204), 노치는 버튼 처리 뒤 순서에서 A의 다음 순위를 고른다.
5. **Given** 노치에 C가 떠 있다, **When** C를 완료한다, **Then** 노치는 남은 할 일 가운데 1위를 고른다.
6. **Given** 점수 있는 할 일과 점수 없는 할 일이 섞여 있다, **When** 노치 순서를 본다, **Then** 점수 있는 할 일이 priority 순으로 앞에, 점수 없는 할 일이 마감일 순으로 뒤에 선다.
7. **Given** 할 일 A의 판단 결과가 있다, **When** A의 제목이나 마감을 고치거나 A에 체크포인트를 남긴다, **Then** A의 판단 입력이 바뀌었으므로 A만 다시 묻는다.
8. **Given** 할 일이 여럿 있다, **When** 일정을 더하거나 고치거나 지운다, 또는 하루가 바뀐 뒤 처음 활성화된다, **Then** 모든 할 일의 판단 입력이 바뀌었으므로 할 일 전체를 다시 묻는다.

### User Story 2 - 키가 없거나 실패해도 앱은 그대로 동작한다 (Priority: P1)

키를 넣지 않았거나, 키가 틀렸거나, 판단 모델이 응답하지 않아도 노치·타이머·버튼은 그대로 동작한다. 점수 없는 할 일은 마감일 순으로 고른다. 키가 틀리면 설정 창 키 칸 옆에 다시 확인해 달라는 문구가 보이고, 키를 다시 저장할 때까지 묻지 않는다. 키가 맞으면 사용자는 "다시 물어보기"로 다시 물을 할 일을 바로 물을 수 있다.

**Why this priority**: FR-14 수용 기준("API 키를 지운 상태로 1시간 동안 표시·타이머·버튼이 동작")이다.

**Independent Test**: 키 없이 할 일 셋(마감 서로 다름)을 넣고 노치가 마감일 순으로 고르는지, 가짜 공급자가 401·타임아웃·잘못된 응답을 낼 때 판단 결과가 저장되지 않고 버튼·타이머가 그대로 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 키가 없다, **When** 할 일 A(마감 모레)·B(마감 내일)·C(마감 없음)를 넣는다, **Then** 노치는 B, A, C 순으로 고른다. 설정 창 priority 칸은 비어 있다.
2. **Given** 키가 틀렸다, **When** 할 일을 저장해 질의가 401로 실패한다, **Then** 그 할 일은 점수 없이 남고, 설정 창 키 칸 옆에 키를 다시 확인해 달라는 문구가 보이며, 키를 다시 저장할 때까지 어떤 할 일도 묻지 않는다. 노치는 바뀌지 않는다.
3. **Given** 판단 모델이 3초 안에 답하지 않는다, **When** 질의가 끝난다, **Then** 그 할 일은 점수 없이 남고, 그동안에도 노치·타이머·버튼은 멈추지 않는다. 다음 활성화 때 그 할 일을 한 번 다시 묻는다.
4. **Given** 점수 없는 할 일이 있고 키가 맞다, **When** 설정 창에서 "다시 물어보기"를 누른다, **Then** 다시 물을 할 일(R-206)을 지금 묻는다.
5. **Given** 키가 저장되어 priority 순으로 고르고 있다, **When** 설정 창에서 키를 지운다, **Then** 노치는 저장된 판단 결과를 쓰지 않고 마감일 순으로 고른다.

### User Story 3 - 키는 Keychain에만 있고 화면에 다시 보이지 않는다 (Priority: P1)

사용자는 설정 창 기본 탭의 키 칸에 키를 붙여 넣고 저장한다. 저장한 뒤에는 키 값이 다시 보이지 않고 "저장돼 있어요"와 지우기 버튼만 보인다. 키는 macOS Keychain에만 있고 앱 DB·설정·로그에는 남지 않는다.

**Why this priority**: 공개 저장소이고 헌법 보안 절의 요구다. US1이 키에 기댄다.

**Independent Test**: 가짜 키 보관함으로 저장·있음 확인·지우기를 시험하고, 저장 뒤 화면 상태가 바뀌는지 스냅샷으로 확인한다. 실제 Keychain 저장과 확인 창 반복 여부는 사람이 개인 팀 서명 빌드(Apple 개발자 계정의 개인 팀으로 서명한 빌드)에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 키가 없다, **When** 설정 창 기본 탭을 연다, **Then** 키 붙여 넣는 칸과 "저장" 버튼이 보인다.
2. **Given** 키 칸에 값을 넣었다, **When** "저장"을 누른다, **Then** 키가 Keychain에 저장되고, 칸 대신 "저장돼 있어요", "지우기", "다시 물어보기"가 보이며, 다시 물을 할 일을 묻는다.
3. **Given** 키가 저장되어 있다, **When** 앱을 다시 켜고 설정 창을 연다, **Then** 키 값은 보이지 않고 "저장돼 있어요"가 보인다.
4. **Given** 키가 저장되어 있고 할 일이 하나도 없다, **When** 키 칸을 본다, **Then** 할 일을 저장하면 키가 맞는지 확인된다는 안내가 보인다.
5. **Given** 앱을 썼다, **When** 앱 DB·설정·로그를 본다, **Then** 키 값이 어디에도 없다.

### Edge Cases

- **질의 중에 그 할 일을 고침:** 고치기 전 내용으로 받은 답은 버린다. 고친 내용은 판단 입력이 달라졌으므로 따로 묻는다.
- **질의 중에 그 할 일을 지움(버림)·완료:** 받은 답을 저장하지 않는다.
- **같은 할 일에 질의가 겹침:** 지금 판단 입력과 같은 입력으로 받은 답만 저장한다.
- **실행 중인 할 일의 판단 결과가 바뀜:** 타이머는 그대로이고, 순서 변화는 다음 고르기(완료·바꾸기·미루기 뒤)부터 쓴다. 노치가 도중에 할 일을 바꾸지 않는다.
- **시작 전 화면(초안)에 떠 있는 할 일보다 priority가 높은 할 일이 새로 생김:** 초안은 그대로 두고, 다음 고르기부터 새 순서를 쓴다.
- **같은 priority:** 마감이 이른 할 일이 앞, 그다음 만든 순.
- **마감이 내일까지(지난 마감 포함):** 모델의 urgency와 상관없이 urgency를 가장 높은 값으로 본다(PRD 7장 하한).
- **질문 버전이 바뀜:** 이전 버전으로 매긴 판단 결과는 쓰지 않고 다시 묻는다.
- **앱을 다시 켬:** 저장된 판단 결과를 그대로 쓰고, 판단 입력이 바뀐 할 일만 다시 묻는다. 노치 순서가 다시 켤 때마다 흔들리지 않는다.
- **완료·버린 할 일:** 묻지 않는다.
- **429·529(속도 제한·과부하)·타임아웃·네트워크·서버 오류:** 그 자리에서 다시 시도하지 않고 점수 없음으로 둔다. 다음 활성화 때 한 번 다시 묻는다. 연속 실패를 막는 장치(서킷브레이커)는 마일스톤 5다.
- **응답에 질문이 빠졌거나 확률이 범위 밖:** 해석 실패로 보고 판단 결과를 저장하지 않는다.
- **Keychain을 읽지 못함(사용자가 확인 창에서 거부 등):** 키 없음으로 보고 묻지 않는다. 저장·지우기에 실패하면 키 칸에 다시 해 달라는 문구를 보인다.
- **앱 DB를 열 수 없음(spec 002 R-119):** 판단 결과를 저장할 곳이 없으므로 묻지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

| R-ID | 요구 | PRD |
|---|---|---|
| R-201 | 판단 질의는 할 일 한 건마다 질문 넷(urgency, impact, concrete, avoiding)을 한 요청으로 묻는다. 판단 입력에는 오늘 날짜와 요일, 그 할 일(제목, 마감, 예상 소요, 이어서 할 일), 일정 목록(이름, 날짜, 중요도), 그 할 일의 마지막 체크포인트(두 줄 중 하나라도 적힌 가장 최근 것의 한 일 줄, 다음 할 일 줄)만 넣는다. 다른 할 일, 미룬 횟수, 이월 횟수, 이전 확률, 사용자 행동 이력은 넣지 않는다 | FR-03 |
| R-202 | 질문의 문구·타입·옵션·임계값은 버전이 붙은 질문 파일 한 벌(v1, 한국어)에 둔다. 문구는 PRD 6장을 따른다. impact 옵션은 낮은 순으로 "조금/꽤/아주"이고, 판단 입력의 일정 중요도도 같은 말로 보낸다. 임계값은 질문 파일의 요청 모델 이름 아래에 둔다. 질문 파일은 앱·시험·시뮬레이터·튜닝 스크립트가 같은 파일을 읽는 공개 계약이다 | FR-03, PRD 6장 |
| R-203 | 판단 질문 blocked는 두지 않는다(사용자 결정 2026-11-06). priority 식과 저장에서도 blocked 항을 뺀다 | PRD 6·7장 변경 |
| R-204 | priority = w_u·urgency + w_i·impact + w_a·aging. urgency·impact는 모델 점수를 0~1로 정규화한 값이고, 마감이 내일까지(지난 마감 포함)이면 urgency를 1로 본다. aging = 미룬 횟수 × (avoiding이 임계값 이상이면 1.5, 아니면 1). 가중치 초기값은 w_u 1.0, w_i 0.7, w_a 0.8이다 | FR-04, PRD 7장 |
| R-205 | 할 일마다 최신 판단 결과(질문 버전, 공급자, 응답 모델 이름, 질문별 확률·신뢰도, 정규화 값, 판단 입력 해시, 매긴 시각) 한 벌을 저장하고 다시 물으면 덮어쓴다. priority는 저장하지 않고 고를 때 R-204로 계산한다(미룬 횟수가 버튼마다 바뀐다). 앱을 다시 켜도 남는다 | FR-04 |
| R-206 | 다시 물을 할 일은 대기·진행 중 할 일 가운데 판단 결과가 없거나, 질문 버전이 다르거나, 지금 판단 입력이 판단 결과를 매길 때와 다른 할 일이다(판단 입력에 오늘 날짜가 있어 하루가 바뀌면 전부 해당한다). 키가 없거나, 401 뒤 키를 다시 저장하지 않았거나, 앱 DB를 열 수 없으면 묻지 않는다 | FR-01, FR-02, PRD 7장 7번(변경) |
| R-207 | 묻는 때: 할 일·일정을 쓴 뒤(노치 빠른 입력 포함), 활성화 때, 키를 저장했을 때, "다시 물어보기"를 눌렀을 때. 같은 판단 입력으로 이미 보낸 할 일은 다시 보내지 않는다. 예외: 실패한 할 일은 다음 활성화 때 한 번 다시 보내고, 키 저장·"다시 물어보기"·앱 재시작 뒤에는 다시 보낸다. 동시에 보내는 질의는 4개까지다 | FR-01, FR-02, FR-14 |
| R-208 | 노치 후보 순서: 점수 있는 대기 할 일을 priority 높은 순으로 앞에, 점수 없는 대기 할 일을 마감일 순(마감 없음은 맨 뒤, 같으면 만든 순)으로 뒤에 둔다. 같은 priority는 마감이 이른 순, 그다음 만든 순이다. 키가 없으면 모든 할 일을 점수 없음으로 본다 | FR-05(임시), FR-04 |
| R-209 | 노치 고르기는 spec 002 R-104(완료·바꾸기·미루기 뒤 다음 할 일을 고르는 순환)를 R-208 순서로 한다: 처음과 완료 뒤에는 1위, 바꾸기·미루기 뒤에는 버튼 처리 뒤 다시 계산한 순서에서 방금 할 일의 다음 순위(끝이면 1위). 실행 중이거나 초안으로 떠 있는 할 일은 판단 결과가 바뀌어도 바꾸지 않는다. 이 규칙은 스케줄러(마일스톤 4) 전 임시 규칙이고, 키가 없을 때의 spec 002 만든 순서 순환을 대신한다 | FR-05(임시) |
| R-210 | 공급자는 TypeSafe Jev 하나(고정 버전 모델)다. 공급자는 바꿔 끼울 수 있는 경계 뒤에 두어 시험·CI·시뮬레이터는 가짜 공급자를 쓰고 실제 API를 부르지 않는다 | FR-14 |
| R-211 | 질의는 3초 안에 끝나지 않으면 실패로 본다. 어떤 실패(키 없음, 401, 429, 529, 그 밖의 서버 오류, 네트워크, 해석 실패)든 그 자리에서 다시 시도하지 않고 그 할 일의 판단 결과를 저장하지 않는다. 질의가 도는 동안과 실패 뒤에도 노치·타이머·버튼은 멈추지 않는다. 코드 폴백은 마감일 정렬만이고 점수 없는 할 일에 확률을 지어내지 않는다 | FR-14, NFR 성능 |
| R-212 | 행동 로그의 판단 칸: 점수 있는 할 일에 버튼을 누르면 그 할 일의 저장된 판단 결과(질문 버전, 공급자, 확률, 판단 입력 해시, 응답 모델 이름)를 남기고, 점수 없는 할 일이면 공급자 `fallback`만 남기고 나머지는 비운다. 노치 선택 규칙 이름은 R-209 규칙의 새 이름이다. 판단 칸에 할 일 제목·체크포인트 본문을 넣지 않는다 | FR-11, FR-03 |
| R-213 | 설정 창 기본 탭 아래에 키 칸을 둔다. 키가 없으면 붙여 넣는 칸과 "저장", 있으면 키 값 대신 "저장돼 있어요"와 "지우기", "다시 물어보기"를 보인다. 할 일이 없으면 할 일을 저장하면 확인된다고 안내한다. 질의가 401로 실패하면 키 칸 옆에 키를 다시 확인해 달라는 문구를 보이고, 키를 다시 저장하거나 지우면 지운다. 저장·지우기에 실패하면 다시 해 달라는 문구를 보인다. 문구는 해요체다. 저장할 때 따로 시험 호출을 하지 않는다 | FR-16(API 키), FR-14 |
| R-214 | 키는 macOS Keychain(service `dev.dongwon.moka`, account `typesafe`)에만 둔다. 앱 DB·설정·로그·화면에 키 값을 다시 보이거나 남기지 않는다 | 헌법 보안, FR-16 |
| R-215 | 설정 창 할 일 탭 목록의 줄마다 priority 숫자 칸(소수 둘째 자리 반올림)을 둔다. 점수 없는 할 일(키 없음 포함)은 비운다. 화면은 HTML 시안을 사람이 확정한 뒤 만든다 | FR-04(확인용) |
| R-216 | 화면 없이 확인하는 시뮬레이터가 가짜 판단 결과를 받아 노치 후보 순서와 고른 할 일, 로그 판단 칸의 공급자(`fake`·`fallback`)를 출력해야 한다. 타이머 시나리오의 기대 출력은 바뀌지 않고, 키 없는 storage 시나리오의 기대 출력은 R-208·R-209대로 새로 정한다. 입력 형식은 [contracts/moka-sim-v1-additions-003.md](contracts/moka-sim-v1-additions-003.md) | ADR-0003 검증 경로 |

### Key Entities

- **판단 결과**: 할 일, 질문 버전, 공급자, 응답 모델 이름, 질문별 확률과 신뢰도, 정규화한 urgency·impact, concrete·avoiding 확률, 판단 입력 해시, 매긴 시각. 할 일마다 하나이고 다시 물으면 덮어쓴다. PRD 9장 `scores`에서 blocked와 priority를 뺀다.
- **질문 파일**: 버전, 요청 모델 이름, 질문 넷의 타입·문구·옵션, 모델별 임계값. 앱과 튜닝 스크립트가 함께 읽는 계약이다.
- **판단 입력**: 오늘, 할 일 한 건, 일정 목록, 마지막 체크포인트. 저장하지 않고 해시만 남긴다.
- **키 보관함**: 키 하나. macOS Keychain.
- **행동 로그**: spec 002 그대로이고, 판단 칸에 값이 들어가기 시작한다.

구조(모듈 경계, 타입, 표)는 [plan.md](plan.md) Summary와 [data-model.md](data-model.md)에 있다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-201**: 할 일을 저장한 뒤 10초 안에 그 할 일에 판단 결과가 붙는다. 시험은 저장 → 질의 → 저장 연결을 가짜 공급자로 확인하고, 10초는 사람이 실제 키로 한 번 확인한다.
- **SC-202**: 판단 요청 어디에도 금지 필드(다른 할 일, 미룬·이월 횟수, 이전 확률, 행동 이력)가 없고, 질문은 넷이며 응답은 질문 넷의 확률이다(단위 시험).
- **SC-203**: 판단 결과가 주어진 할 일들의 노치 순서와 고르기가 R-208·R-209와 같다(단위 시험, 시뮬레이터, 사람이 설정 창 priority 칸과 노치를 비교).
- **SC-204**: 키를 지운 상태로 1시간 동안 표시·타이머·버튼이 동작하고 노치는 마감일 순으로 고른다(주입한 시계로 시험, 사람은 키를 지우고 몇 분 동안 시작·완료·바꾸기가 되는지 확인).
- **SC-205**: 판단 실패 일곱 종류(키 없음, 401, 타임아웃, 429·529, 그 밖의 서버 오류, 네트워크, 해석 실패)에서 판단 결과가 저장되지 않고 노치 상태가 바뀌지 않는다(가짜 공급자 시험).
- **SC-206**: 다시 물을 할 일(R-206)과 묻는 때·다시 보내지 않기·실패 뒤 한 번 다시(R-207)가 규칙대로다(단위 시험과 앱 시험).
- **SC-207**: 시험·CI·시뮬레이터는 실제 판단 API를 한 번도 부르지 않고, 실제 Keychain과 앱 DB를 열지 않는다.
- **SC-208**: 앱 DB·설정·로그 어디에도 키 값이 없다(시험으로 저장 경로 확인, 사람은 키를 저장한 뒤 설정 창과 앱 로그에 키가 보이지 않는지 확인).
- **SC-209**: 사람이 확인용 빌드에 실제 키를 넣고 할 일 하나를 저장했을 때 판단 결과가 붙는다. 결과는 PASS/FAIL과 응답 필드 이름만 기록하고 응답 원문은 남기지 않는다.
- **SC-210**: 키 칸 상태 여섯(키 없음, 저장됨, 저장됨·할 일 없음 안내, 키 확인 필요(401 문구, "다시 물어보기" 꺼짐), 저장·지우기 실패 문구, 저장 불가)이 R-213대로 보인다(스냅샷).

## Assumptions

- 사용자는 작성자 1인, macOS 14 이상이다. 판단 모델에 할 일 제목, 이어서 할 일, 체크포인트 두 줄, 일정 이름이 보내지는 것은 제품 전제다(PRD 2장).
- 판단 모델은 호출당 수십 밀리초, 입력 100만 토큰당 4.2센트다(PRD 2장). 할 일 수십 건을 하루 한 번 다시 묻는 비용은 작다.
- 판단 입력의 일정 목록은 PRD대로 모든 일정을 넣는다. 지난 일정을 뺄지는 마일스톤 5 튜닝에서 본다.
- 점수 정규화: urgency는 옵션 네 단계(0~3)를 3으로, impact는 세 단계(0~2)를 2로 나눈다. concrete는 저장만 하고 이번에는 쓰지 않는다(FR-13은 다음 spec).
- 이월 횟수는 마일스톤 4에서 생기므로 aging에는 미룬 횟수만 들어간다.
- 가중치 초기값은 코드 기본값 한 곳에 두고, 질문 임계값은 질문 파일에 둔다(AGENTS.md).
- 확인용 빌드는 개인 팀 서명이다(ADR-0005, 사용자가 2026-11-06 서명 파일과 인증서를 준비함). 다시 빌드해도 Keychain 확인 창이 반복되지 않는지는 사람 확인이다.
- TypeSafe API 형식은 공식 문서(2026-11-06 확인)를 따른다. 문서와 실제가 다를 수 있으니 첫 실제 호출에서 필드 이름을 대조한다.
- 화면 문구는 고객용 해요체다. 문구는 시안에서 정한다.
- 승인 항목(헌법 I: 사람 승인 없이 바꾸지 않는 계약): 판단 결과 표, 질문 파일 형식과 위치, 공급자 경계, 로그의 새 선택 규칙 이름, 시뮬레이터 입력 확장. 사용자가 2026-11-06~07에 정했고([plan.md](plan.md) "승인 항목"), 구현 PR "사람이 볼 결정"에 다시 올린다.

## Non-Goals

- 다음 spec(v1 태그 전): FR-13 구체화 게이트, 노치의 이유 3개 화면(FR-04 화면), 온보딩 키 단계(FR-21 키), 노치 "키 확인" 표시.
- 마일스톤 4: quantum 만료 때 상위 5개 재점수, 가중 라운드로빈, 이월 카드, 아침 워밍업.
- 마일스톤 5: 서킷브레이커(연속 실패 시 일정 시간 질의를 멈추는 장치), 429 백오프, 실행 중 질문(stop_cost, on_task), 영어 질문 v1-en, 라벨셋 비교와 튜닝 리포트.
- 하지 않음: 두 번째 공급자(OpenRouter Decision-1, Vercel), 저장할 때 키 시험 호출, 키 값 다시 보기, 질의 취소·우선순위 큐.

소수 의견: 질문 파일 위치(위험 자리, 저장소 루트에 두고 코어에 주입), `moka-sim` 확장(실행 자리, 이번에는 넓히지 않고 단위 시험만), 마감 임박 예외(실행 자리, 점수 없는 마감 임박 할 일을 앞에). 이유는 research R9·R13·R17.

위험(완화는 [plan.md](plan.md) "위험", 번호가 같다):

- 위험 1(일정): 검증 시작 2026-11-10은 고정이고 마일스톤 4·5가 남았다. 필수는 R-201~R-214다. 밀리면 R-215(priority 칸, 시안 확정) → R-216(시뮬레이터) 순으로 다음 spec에 넘긴다.
- 위험 2(실제 응답 형식): 공식 문서와 실제 응답이 다르면 해석 코드를 고친다. 첫 실제 호출은 사람만 할 수 있다.
- 위험 3(Keychain): 확인 창 반복, 접근성 속성은 리눅스 CI로 확인할 수 없고 사람이 개인 팀 서명 빌드로 확인한다.
- 위험 4(되돌리기 어려운 계약): 판단 결과 표, 질문 파일 형식, 로그의 새 선택 규칙 이름은 한 번 내면 바꾸기 비싸다. 열과 값을 적게 두었다.
- 위험 5(개인정보): 할 일 제목, 이어서 할 일, 체크포인트 두 줄, 일정 이름이 외부 판단 모델로 간다. 로그와 판단 결과에는 제목·본문을 남기지 않는다.
- 위험 6(PRD와 다름): blocked 삭제, impact 3단계 옵션 문구, 6시간 캐시 대신 입력 해시 규칙은 PRD 6·7장과 다르다. PRD는 저장소 밖 문서라 고칠 문장을 사람에게 알린다.
- 위험 7(실패 뒤 순서): 키가 있을 때 오늘 마감 할 일의 질의가 실패하면 점수 없는 무리로 가 점수 있는 할 일 뒤에 선다. 회복은 다음 활성화 때 한 번 다시 묻기, "다시 물어보기", 앱 재시작, 다음 날이다. 설정 창 priority 칸이 비어 보여 알아챌 수 있다(사용자 결정 2026-11-07).
- 위험 8(리눅스 리소스): `Bundle.module`이 리눅스 CI에서 질문 파일을 읽지 못하면 단위 1 첫 시험에서 드러난다.
- 위험 9(몰림 중 고친 할 일): 하루가 바뀐 뒤 다시 묻는 동안 이미 점수가 있는 할 일을 고치거나, 키를 처음 저장한 직후 새 할 일을 저장하면 10초(SC-201)를 넘길 수 있다(사용자 결정 2026-11-07).
