# Feature Specification: 판단 결과 화면 연결 (마일스톤 3 나머지)

**Feature Branch**: `chore/spec-004-decision-screens`

**Created**: 2026-11-10

**Status**: Draft

**Input**: PRD(`~/Dev/ai-platform/projects/moka/prd.md`, 저장소 밖) 12장 마일스톤 3 가운데 [spec 003](../003-decision-model/spec.md)(판단 모델 연동 MVP, main `907d1d0`)이 Non-Goals로 미룬 넷을 담는다. FR-04 이유 표시, FR-13 구체화 게이트, FR-16·FR-21 온보딩 키 단계, 노치 키 확인 표시다. spec 003의 판단 결과(`scores` 표, `TaskScore`), 점수 규칙(`ScoreRules`), 순위(`ranks`), 키 확인 필요(`keyNeedsCheck`)를 그대로 쓴다.

결정 이력:
- 이 초안은 PRD와 spec 003 결정을 근거로 메인 세션이 썼다. 사용자에게 묻지 않은 해석은 Assumptions에 있다.
- 확인 질문 셋은 2026-11-10 무인 실행에서 debate로 정했다. 세 질문 모두 3:0이고 사람 확인을 기다린다.
  - Q1(R-307): 게이트는 시작 위에 뜨고, "지금은 넘기기"를 누르면 통과로 본다.
  - Q2(R-309): 통과 기록과 남은 횟수는 메모리에만 둔다.
  - Q3(R-316): 접힌 노치에는 키 확인 표시를 두지 않는다.
- 노치 키 확인 표시는 2026-11-10 사용자가 spec 003 확인 중에 지적한 불편에서 나왔다. 지금은 설정 창 기본 탭 키 칸에만 401 문구가 보여, 노치와 할 일 탭에서는 키가 틀린 것을 알 수 없다.

## 용어

spec 003 용어(판단 모델, 키, 판단 입력, 판단 결과, priority, 활성화, 초안, 보내기 장부)를 그대로 쓴다. 이 spec에서 새로 쓰는 말은 다음과 같다.

- **노치 할 일**: 지금 노치에 떠 있는 할 일. 시작 전(초안)이거나 도는 중이다. 용어집의 "현재 할 일"과 같고, 이 spec에서는 시작 전도 포함한다.
- **이유 줄**: 노치 펼친 화면에서 노치 할 일이 왜 떴는지 보이는 한 줄. 마감까지 남은 날, 손해, 미룬 횟수로 이뤄진다(PRD FR-04).
- **쓰는 판단 결과**: spec 003 data-model §3의 `usable` 판단 결과. 키가 있고 질문 버전이 지금과 같은 판단 결과이며, 판단 입력이 바뀌었어도 다시 묻기 전까지는 쓴다.
- **새 판단 결과**: 지금 판단 입력과 같은 해시로 매긴 판단 결과. 쓰는 판단 결과 가운데 낡지 않은 것이다.
- **구체화 게이트**: concrete 확률이 낮은 할 일이 시작 전으로 뜰 때 첫 행동 한 줄을 받는 노치 화면(PRD FR-13). 줄여서 게이트라 쓴다.
- **첫 행동**: 할 일의 `firstAction`. 화면 이름은 "이어서 할 일"이다(spec 002 R-109, 용어집).
- **물을 수 있음**: spec 003 data-model §6 "묻지 않는 경우"에 들지 않는 상태. 판단 기능이 켜져 있고, 키가 있고, 키 확인 필요가 아니며, 판단 결과 저장소가 있다.
- **키 확인 필요**: 질의가 401·403으로 실패한 뒤 키를 다시 저장하거나 지우기 전까지의 상태(spec 003 R-213, `keyNeedsCheck`).

## Goals

- 완료 조건(PRD FR-04 수용 기준): 노치 펼침에서 현재 할 일의 이유 3개(D-n, 손해, 미룬 횟수)가 보인다.
- 완료 조건(PRD FR-13 수용 기준): 통과한 첫 행동이 제목 아래 표시된다.
- 완료 조건(PRD FR-21 수용 기준): 키 없이 온보딩을 끝내도 노치에 할 일이 뜬다.
- 키가 틀려 판단 모델에 묻지 못하는 동안 사용자가 노치와 설정 창 할 일 탭에서도 그 사실을 안다.
- 판단 공급자는 spec 003 그대로 TypeSafe Jev 하나이고, 스키마는 바꾸지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 노치를 펼치면 이 할 일이 왜 떴는지 보인다 (Priority: P1)

사용자는 노치를 펼쳐 노치 할 일의 제목 아래에서 이유 줄을 본다. 이유 줄에는 마감까지 남은 날, 이 일을 안 했을 때의 손해, 미룬 횟수가 있다. 사용자는 이 줄을 보고 노치가 고른 순서를 믿을지 판단한다.

**Why this priority**: PRD FR-04 수용 기준이고, 마일스톤 3의 남은 필수 항목이다. 다른 이야기와 상관없이 혼자 확인할 수 있다.

**Independent Test**: 가짜 판단 결과를 넣은 할 일 셋(마감·손해·미룬 횟수가 서로 다름)으로 시작 전과 도는 중 펼친 화면을 스냅샷으로 찍고, 이유 줄 글자를 MokaCore 단위 시험으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 할 일 A(마감 사흘 뒤, 쓰는 판단 결과의 손해 "꽤", 미룬 횟수 2)가 시작 전으로 떠 있다, **When** 노치를 펼친다, **Then** 제목 아래 이유 줄에 마감까지 남은 날 3일, 손해 "꽤", 미룬 횟수 2번이 보인다.
2. **Given** A가 도는 중이다, **When** 노치를 펼친다, **Then** 시작 전과 같은 이유 줄이 보인다.
3. **Given** 할 일 B는 마감이 오늘이다, **When** B가 노치 할 일로 펼쳐진다, **Then** 남은 날 칸은 오늘이 마감이라고 보인다.
4. **Given** 할 일 C에 쓰는 판단 결과가 없다(키 없음 포함), **When** C가 노치 할 일로 펼쳐진다, **Then** 이유 줄에는 남은 날과 미룬 횟수만 있고 손해 칸은 없다. 손해를 지어내지 않는다.
5. **Given** A가 도는 중이고 A를 다시 물어 판단 결과가 바뀌었다, **When** 노치 펼친 화면을 본다, **Then** 이유 줄의 손해가 새 값으로 바뀌고 노치 할 일은 바뀌지 않는다.
6. **Given** A의 시간이 끝나 두 줄 입력 칸이 보인다, **When** 노치를 본다, **Then** 이유 줄은 보이지 않는다(spec 002 R-109의 시간 끝 화면과 같은 이유).

### User Story 2 - 막연한 할 일은 첫 행동 한 줄을 적고 시작한다 (Priority: P1)

판단 모델이 "2분 안에 첫 행동을 시작할 수 있다"고 보지 않는 할 일이 시작 전으로 뜨면, 노치는 "첫 행동 한 줄?"을 묻는다. 사용자가 한 줄을 적으면 그 줄이 할 일의 첫 행동이 되고, 판단 모델이 다시 판정한다. 통과하면 첫 행동이 제목 아래 보이고 사용자는 그대로 시작한다. 세 번 적어도 통과하지 못하면 통과로 보고 더 묻지 않는다.

**Why this priority**: PRD FR-13(P0) 수용 기준이다. 판단 결과의 concrete 확률은 spec 003부터 저장만 하고 쓰지 않았다.

**Independent Test**: 가짜 공급자가 첫 판정에서 concrete 0.3, 첫 행동을 적은 뒤 재판정에서 0.8을 내게 하고, 게이트가 열림, 제출, 재판정, 통과, 첫 행동 표시까지를 앱 시험으로 확인한다. 세 번 모두 0.3이면 세 번째 제출 뒤 통과로 보는지 확인한다. 실제 키로는 사람이 확인용 빌드에서 한 번 본다.

**Acceptance Scenarios**:

1. **Given** 물을 수 있고, 할 일 A의 쓰는 판단 결과에서 concrete가 0.3(임계값 0.5 미만)이다, **When** A가 시작 전으로 뜨고 노치를 펼친다, **Then** 게이트가 "첫 행동 한 줄?"과 한 줄 입력 칸을 보인다.
2. **Given** 게이트가 열려 있다, **When** 사용자가 "가짜 첫 행동"을 적어 제출한다, **Then** A의 첫 행동이 "가짜 첫 행동"으로 저장되고, A의 판단 입력이 바뀌었으므로 A를 다시 묻는다. 게이트는 확인하는 중이라고 보인다.
3. **Given** 재판정에서 A의 새 판단 결과 concrete가 0.8이다, **When** 답이 저장된다, **Then** 게이트가 닫히고 제목 아래에 "가짜 첫 행동"이 이어서 할 일로 보인다.
4. **Given** 재판정에서 concrete가 다시 0.3이다, **When** 답이 저장된다, **Then** 게이트가 다시 한 줄을 묻는다. 칸에는 방금 적은 줄이 들어 있어 고쳐 쓸 수 있다.
5. **Given** 세 번째 제출의 재판정도 concrete가 임계값 미만이다, **When** 답이 저장된다, **Then** 게이트는 통과로 보고 닫히며, 마지막에 적은 첫 행동이 제목 아래 보인다.
6. **Given** 게이트가 재판정을 기다린다, **When** 질의가 타임아웃·서버 오류·해석 실패로 끝나거나 401로 키 확인 필요가 된다, **Then** 게이트는 그 제출에서 통과로 보고 닫힌다. 노치·타이머·버튼은 내내 멈추지 않는다.
7. **Given** 키가 없거나, 키 확인 필요이거나, A에 쓰는 판단 결과가 없다, **When** A가 시작 전으로 뜬다, **Then** 게이트는 열리지 않는다.
8. **Given** A의 concrete가 0.7(임계값 이상)이다, **When** A가 시작 전으로 뜬다, **Then** 게이트는 열리지 않는다.
9. **Given** 게이트가 열려 있다, **When** 사용자가 시작을 누르려 한다, **Then** 게이트 입력 칸이 열린 동안 Enter는 제출이고, 시작 버튼은 Enter로 눌리지 않는다. 사용자가 "지금은 넘기기"를 누르면 게이트가 통과로 닫히고 Enter로 시작할 수 있다. (debate 3:0, 무인 실행 2026-11-10, 사람 확인 대기)
10. **Given** 게이트가 열려 있다, **When** 사용자가 "지금은 넘기기"를 누른다, **Then** 게이트가 닫히고 첫 행동은 바뀌지 않으며 다시 묻지 않는다. 앱을 끄기 전까지 그 할 일이 다시 시작 전으로 떠도 게이트는 열리지 않는다.
11. **Given** 게이트가 열려 있다, **When** 사용자가 시작 버튼을 눌러 시작한다, **Then** 게이트가 닫히고 타이머가 돈다. 통과로 보지 않으므로 그 할 일이 다음에 시작 전으로 뜨면 남은 횟수로 다시 연다.

### User Story 3 - 처음 켤 때 키를 넣거나 건너뛴다 (Priority: P2)

처음 앱을 켠 사용자는 온보딩 첫 단계에서 TypeSafe 키를 발급받는 방법을 보고 키를 붙여 넣는다. 키가 없으면 건너뛰고, 노치는 마감이 가까운 순으로 할 일을 띄운다. 이미 온보딩을 끝낸 사용자에게는 다시 보이지 않고, 키는 spec 003의 설정 창 기본 탭 키 칸에서 넣는다.

**Why this priority**: PRD FR-16·FR-21(P0)이지만 작성자 1인은 이미 온보딩을 끝냈고 설정 창 키 칸이 있다. 새 사용자 첫 실행에만 보인다.

**Independent Test**: 가짜 설정 저장소(온보딩 안 끝남)와 가짜 키 보관함으로 키 단계 저장·건너뛰기·실패를 앱 시험으로 확인하고, 키 단계 상태를 스냅샷으로 찍는다. 새 사용자 첫 실행은 사람이 macOS 새 사용자 계정에서 본다(spec 002 quickstart와 같은 방법).

**Acceptance Scenarios**:

1. **Given** 온보딩을 끝내지 않았고 키가 없다, **When** 앱을 처음 켠다, **Then** 온보딩 첫 단계가 키 단계이고 발급 안내 한 줄, TypeSafe 발급 페이지 링크, 붙여 넣는 칸, "건너뛰기", "다음"이 보인다. 단계 표시는 세 단계 가운데 첫째다.
2. **Given** 키 단계에서 칸에 키를 붙여 넣었다, **When** "다음"을 누른다, **Then** 키가 Keychain에 저장되고 일정 단계로 넘어간다. 키 값은 다시 보이지 않는다.
3. **Given** 키 단계에서 칸이 비어 있다, **When** 키 단계를 본다, **Then** "다음"은 꺼져 있고 "건너뛰기"는 켜져 있다.
4. **Given** 키 단계에서 "건너뛰기"를 눌렀다, **When** 나머지 두 단계를 끝내고 할 일을 넣는다, **Then** 노치에 마감일 순으로 할 일이 뜬다(spec 003 R-208).
5. **Given** 키 저장이 실패한다, **When** "다음"을 누른다, **Then** 키 단계에 머물고 다시 해 달라는 문구가 보이며, "건너뛰기"는 그대로 켜져 있다.
6. **Given** 키를 저장한 뒤 온보딩을 끝내지 않고 앱을 껐다, **When** 다시 켠다, **Then** 온보딩이 처음부터 다시 보이고, 키 단계는 키가 저장되어 있다고 보이며 "다음"으로 넘어갈 수 있다.
7. **Given** 온보딩을 이미 끝냈다, **When** 앱을 켠다, **Then** 온보딩은 보이지 않는다(spec 002 R-116 그대로).

### User Story 4 - 키가 맞지 않으면 노치와 할 일 탭에서도 알 수 있다 (Priority: P2)

질의가 401로 실패하면 지금은 설정 창 기본 탭 키 칸에만 문구가 보인다. 이 이야기 뒤로는 노치를 펼쳤을 때와 설정 창 할 일 탭에서도 키를 확인해 달라는 한 줄이 보이고, 그 줄에서 바로 기본 탭 키 칸으로 갈 수 있다.

**Why this priority**: 2026-11-10 사용자 확인 중 지적된 불편이다. 키 확인 필요인 동안에는 새 할 일에 판단 결과가 붙지 않는데, 사용자는 노치 순서만 보고 알아채기 어렵다(spec 003 위험 7).

**Independent Test**: 가짜 공급자가 401을 내게 해 키 확인 필요를 만들고, 노치 펼친 화면(빈 상태, 시작 전, 도는 중)과 할 일 탭을 스냅샷으로 찍는다. 키를 다시 저장하거나 지우면 표시가 사라지는지 앱 시험으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 키 확인 필요다, **When** 노치를 펼친다(빈 상태, 시작 전, 도는 중 어느 것이든), **Then** 키를 확인해 달라는 한 줄과 설정을 여는 동작이 보인다.
2. **Given** 노치에 키 확인 한 줄이 보인다, **When** 그 동작을 누른다, **Then** 설정 창이 기본 탭으로 열린다.
3. **Given** 키 확인 필요다, **When** 설정 창 할 일 탭을 연다, **Then** 목록 위에 키를 확인해 달라는 한 줄과 기본 탭으로 가는 동작이 보인다.
4. **Given** 키 확인 필요다, **When** 사용자가 키를 다시 저장하거나 지운다, **Then** 노치와 할 일 탭의 표시가 함께 사라진다.
5. **Given** 키가 없다(사용자가 넣지 않음), **When** 노치와 할 일 탭을 본다, **Then** 키 확인 표시는 보이지 않는다. 키 없음은 사용자가 고른 상태다.
6. **Given** 키 확인 필요다, **When** 접힌 노치를 본다, **Then** 접힌 노치는 spec 001·002 모양 그대로이고 키 확인 표시가 없다. (debate 3:0, 무인 실행 2026-11-10, 사람 확인 대기)

### Edge Cases

- **이유 줄, 마감 없음:** 남은 날 칸에 마감이 없다고 보인다.
- **이유 줄, 지난 마감:** 남은 날 칸에 마감이 지났다고 보인다(며칠 지났는지 포함).
- **이유 줄, 하루가 바뀜:** 남은 날은 spec 002 R-114 하루 경계의 오늘로 센다. 하루 시작 시각을 지나면 다음 그리기에서 하루 줄어든다.
- **이유 줄, 미룬 적 없음:** 미룬 횟수 칸은 0번도 보인다. 세 칸 자리를 지켜 화면이 할 일마다 흔들리지 않게 한다.
- **이유 줄, 키를 지움:** 쓰는 판단 결과가 없어지므로 손해 칸이 사라진다(spec 003 R-208과 같은 기준).
- **이유 줄, 판단 입력이 바뀌어 다시 묻는 중:** 다시 묻기 전까지 쓰는 판단 결과의 손해를 그대로 보인다(spec 003 data-model §3).
- **게이트, 같은 줄을 다시 제출:** 첫 행동이 이미 같은 줄이면 판단 입력이 바뀌지 않아 다시 묻지 않는다(보내기 장부). 이 제출은 지금 새 판단 결과로 판정하고 한 번으로 센다.
- **게이트, 판단 결과가 늦게 붙음:** 시작 전으로 뜬 뒤에 판단 결과가 붙어 concrete가 임계값 미만이면, 아직 시작 전이면 게이트를 연다. 이미 시작했으면 열지 않는다.
- **게이트, 기다리는 동안 다른 할 일·새 할 일·버림:** 노치 할 일이 바뀌면 게이트를 닫는다. 이미 저장한 첫 행동과 다시 묻기는 그대로 둔다. 그 할 일이 다시 시작 전으로 뜨면 남은 횟수로 이어서 연다.
- **게이트, 기다리는 동안 하루가 바뀌거나 일정이 바뀜:** 모든 할 일을 다시 묻는 줄에 섞인다. 게이트는 그 할 일의 새 판단 결과가 저장될 때 판정한다. 늦어질 수 있다(위험 2).
- **게이트, 재판정에서 urgency·impact도 바뀜:** spec 003 R-201대로 질문 넷을 함께 묻으므로 priority가 바뀔 수 있다. 시작 전으로 떠 있는 할 일은 바꾸지 않는다(spec 003 R-209).
- **게이트, 질문 버전이 바뀜:** 이전 버전 판단 결과는 쓰는 판단 결과가 아니므로 새 판단 결과가 붙을 때까지 게이트를 열지 않는다.
- **게이트, 앱 DB를 열 수 없음:** 물을 수 없으므로 게이트를 열지 않는다(spec 002 R-119).
- **게이트, 첫 행동 저장 실패:** 게이트에 머물고 다시 해 달라는 문구를 보인다. 횟수로 세지 않는다.
- **온보딩, 키가 이미 Keychain에 있음:** 키 단계는 저장되어 있다고 보이고 붙여 넣는 칸 대신 "다음"만 켠다.
- **온보딩, Keychain을 읽지 못함:** spec 003처럼 키 없음으로 보고 붙여 넣는 칸을 보인다.
- **온보딩, 앞뒤 공백·줄바꿈:** 저장 전에 지운다(spec 003 data-model §9). 지우고 비면 "다음"이 꺼진다.
- **키 확인 표시, 키 확인 필요 중 판단 결과:** spec 003 `usable`은 키가 있으면 저장된 판단 결과를 계속 쓴다. 그래서 순서는 마감일 순이 아닐 수 있고, 표시 문구는 순서가 마감일 순이라고 말하지 않는다.
- **키 확인 표시, 앱을 다시 켬:** 키 확인 필요는 메모리 값이라 다시 켜면 사라진다. 다음 질의가 다시 401이면 다시 보인다(spec 003 그대로).
- **키 확인 표시, 노치 빈 상태의 저장 불가 문구:** 앱 DB를 열 수 없으면 판단 결과를 저장할 곳이 없어 묻지 않으므로 키 확인 필요가 생기지 않는다. 두 문구가 겹치지 않는다.

### Key Entities

- **이유 줄**: 노치 할 일의 남은 날, 손해, 미룬 횟수. 저장하지 않고 그릴 때마다 할 일, 쓰는 판단 결과, 오늘로 만든다.
- **게이트 상태**: 할 일마다 제출 횟수, 기다리는 판단 입력 해시, 통과 여부. 메모리에만 두고 앱을 다시 켜면 사라진다(R-309). 스키마와 설정은 바꾸지 않는다.
- **첫 행동**: spec 002의 할 일 칸 그대로. 게이트가 둘째로 쓰는 곳이 된다.
- **키 확인 필요**: spec 003 메모리 값 그대로. 표시하는 곳이 셋(기본 탭 키 칸, 노치, 할 일 탭)이 된다.
- **판단 결과·질문 파일·키 보관함**: spec 003 그대로 읽기만 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-301**: 노치 시작 전·도는 중 펼친 화면에 노치 할 일의 이유 줄이 보이고, 남은 날·손해·미룬 횟수 글자가 R-302·R-303·R-304와 같다(MokaCore 단위 시험, 스냅샷, 사람이 실제 판단 결과로 한 번 확인).
- **SC-302**: 쓰는 판단 결과가 없는 할 일의 이유 줄에 손해 칸이 없다(단위 시험 3종: 키 없음, 판단 결과 없음, 질문 버전 다름).
- **SC-303**: concrete가 임계값 미만인 할 일이 시작 전으로 뜨면 게이트가 열리고, 제출 뒤 재판정에서 통과하면 1초 안에 게이트가 닫히고 첫 행동이 제목 아래 보인다(가짜 공급자 앱 시험, 기다림은 가짜 공급자를 풀어 줘서 만든다).
- **SC-304**: 세 번 제출해도 통과하지 못한 할 일은 세 번째 재판정 뒤 통과로 보고, 그 뒤 같은 할 일이 다시 시작 전으로 떠도 게이트가 열리지 않는다(앱 시험). "지금은 넘기기"를 누른 할 일도 같다. 앱을 다시 켜면 기록이 사라져 다시 열릴 수 있다(R-309).
- **SC-305**: 재판정 실패 일곱 종류(spec 003 SC-205와 같은 목록)마다 게이트는 그 제출에서 통과로 보고, 노치 상태와 타이머는 바뀌지 않는다(가짜 공급자 시험).
- **SC-306**: 게이트 제출로 생긴 질의는 spec 003 R-207 보내기 규칙(같은 해시 한 번, 동시 4개)을 따르고, 별도 질의 경로가 없다(앱 시험에서 가짜 공급자가 받은 요청 수와 해시를 센다).
- **SC-307**: 키 없이 온보딩 세 단계를 끝내는 데 조작이 세 번(건너뛰기, 건너뛰기, 시작하기)이고, 끝낸 뒤 할 일을 넣으면 노치에 뜬다(앱 시험, 사람이 새 사용자 계정에서 한 번 확인).
- **SC-308**: 온보딩 키 단계에서 저장한 키는 Keychain에만 있고 설정·앱 DB·로그에 없다(spec 003 SC-208과 같은 시험을 온보딩 경로로).
- **SC-309**: 키 확인 필요가 켜지면 노치 펼친 화면 세 상태와 할 일 탭에 표시가 보이고, 키를 저장하거나 지우면 세 곳 모두에서 사라진다(앱 시험과 스냅샷).
- **SC-310**: 시험·CI는 실제 판단 API를 한 번도 부르지 않고 실제 Keychain과 앱 DB를 열지 않는다. 기존 spec 001·002·003 시험과 시뮬레이터 기대 출력은 바뀌지 않는다. 바뀌는 스냅샷 참조 이미지(펼친 화면에 이유 줄이 더해짐, 온보딩 단계 표시)는 PR에 이유를 적는다.

## Assumptions

- 사용자는 작성자 1인, macOS 14 이상이다. 판단 공급자는 TypeSafe Jev 하나다(spec 003 R-210).
- spec 003은 main `907d1d0`에 병합되어 있다. 판단 결과 표, 쓰는 판단 결과 규칙, 다시 묻기 규칙, 보내기 장부, 키 칸 여섯 상태를 바꾸지 않고 쓴다.
- FR-04 "손해"는 impact 판단 질문이다. PRD 6장은 옵션이 "보통/큼/치명적"이지만 spec 003 R-202에서 "조금/꽤/아주"로 바꿨으므로 화면도 그 말을 쓴다.
- impact 정규화 값(0~1)은 옵션 셋에 맞춰 반올림한다. 0.25 미만은 "조금", 0.75 이상은 "아주", 그 사이는 "꽤"다. 경계값은 구현 PR "가정"에 적는다.
- 이유 줄은 PRD FR-06 펼친 화면의 "이유"다. FR-06의 "다음 2개"는 이 spec 범위 밖이다.
- 이유 줄은 세 칸 자리를 지키되 쓰는 판단 결과가 없으면 손해 칸만 뺀다. 판단 결과가 없는데 손해를 보이면 R-211(확률을 지어내지 않음)과 어긋난다.
- PRD 6장은 재판정 질문을 concrete 하나로 적었지만, spec 003 R-201은 할 일마다 질문 넷을 한 요청으로 묻는다. 새 질의 경로 없이 넷을 함께 다시 묻는다. 그 결과 urgency·impact가 바뀌어 순서가 바뀔 수 있다.
- 첫 행동은 판단 입력에 이미 들어 있다(코드 `JudgmentState.build`의 `first_action`). 그래서 첫 행동을 저장하면 할 일 다시 읽기(`reloadTasks`)가 다시 묻기(`requestScores`)를 부르고, 해시가 달라져 그 할 일이 다시 물을 할 일이 된다. 게이트가 따로 확인할 것은 세 가지다. (1) `usable`이 해시가 다른 낡은 판단 결과도 쓰므로 판정은 해시가 같은 새 판단 결과로만 한다. (2) 실패한 질의는 같은 해시로 다음 활성화까지 다시 보내지 않으므로 실패를 통과로 본다. (3) 물을 수 없으면 재판정이 없으므로 게이트를 열지 않는다.
- 게이트는 시작 전 할 일에만 연다. 용어집의 "현재 할 일"은 타이머가 붙은 할 일이지만, 도는 중에 입력을 받으면 일하는 흐름을 끊는다. 시작 전은 PRD FR-13 "현재 할 일로 뜰 때"의 가장 이른 때다.
- 같은 줄을 다시 제출하면 질의가 나가지 않는다. 지금 새 판단 결과로 판정하고 한 번으로 센다.
- 게이트 입력 칸의 글자 수 제한과 줄바꿈 처리는 체크포인트 다음 할 일 줄과 같다.
- 게이트 제출은 행동 로그에 남기지 않는다. PRD FR-11은 "모든 버튼·카드 입력" 기록을 요구하지만, 새 사용자 행동 값은 공개 계약(로그 스키마의 값) 변경이라 이 spec에서 하지 않는다(위험 4).
- 온보딩 단계 순서는 PRD FR-21대로 키, 일정, 기본값이다. 키 저장은 키 단계 "다음"에서 바로 한다. 일정·설정이 "시작하기"에서 한꺼번에 저장되는 spec 002 규칙과 다른 이유는, Keychain은 앱 DB와 다른 저장소라 한꺼번에 되돌릴 수 없고, 설정 창 키 칸과 같은 동작을 쓰는 편이 단순하기 때문이다.
- TypeSafe 발급 페이지 주소는 공식 문서에서 사람이 확인한 주소를 쓴다. 앱은 링크를 기본 브라우저로 열기만 한다.
- 노치 키 확인 표시는 펼친 화면 한 줄이고, 누르면 설정 창 기본 탭이 열린다. 할 일 탭 표시도 같은 동작이다. 설정 창을 여는 기존 동작(spec 001 R-012 메뉴)을 쓴다.
- 화면 문구는 고객용 해요체다. 막을 때는 이유를 안내한다. 문구는 시안에서 확정한다.
- 승인 항목(헌법 I): 이 spec은 스키마, 질문 파일, 판단 공급자 경계, 시뮬레이터 시나리오 형식, 로그 값 집합을 바꾸지 않는다. 사람이 정할 일은 화면 시안 확정과 debate로 정한 Q1~Q3의 확인이다.

## Non-Goals

- 마일스톤 4: quantum 만료 때 상위 5개 재점수, 가중 라운드로빈, 이월 카드, 아침 워밍업(concrete 0.8 이상 규칙 포함), 이월 횟수의 aging 반영.
- 마일스톤 5: FR-12 불확실 시 질의, 서킷브레이커, 429 백오프, 실행 중 질문(stop_cost, on_task), 영어 질문 v1-en, 라벨셋 비교.
- PRD FR-06의 "다음 2개" 표시와 alert(이월 카드, 불확실 질의, 딴짓 알림).
- 게이트 제출의 행동 로그 기록(새 사용자 행동 값).
- 이미 온보딩을 끝낸 사용자에게 키 단계를 다시 보이기. 키는 설정 창 기본 탭에서 넣는다.
- 두 번째 공급자(OpenRouter Decision-1, Vercel), 저장할 때 키 시험 호출, 키 값 다시 보기.
- 시뮬레이터(`moka-sim`) 입력 확장. 이유 줄과 게이트 규칙은 MokaCore 단위 시험과 앱 시험으로 확인한다.

## 대안과 위험

대안(고른 안과 기각한 안, 메인 세션 초안이며 사람 확인 전):

| 결정 | 기각한 안(한 줄 이유) | 근거 |
|---|---|---|
| 재판정은 spec 003 다시 묻기 규칙으로 | concrete 하나만 묻는 새 질의 경로(공급자 경계·질문 파일 계약을 바꾸고 판단 결과 한 벌 원칙이 깨짐) | spec 003 R-201·R-205·R-206, PRD 6장 |
| 판정은 해시가 같은 새 판단 결과로만 | 쓰는 판단 결과 그대로(제출 직후 낡은 concrete로 바로 다시 실패 판정) | spec 003 data-model §3 |
| 재판정 실패는 통과 | 다음 활성화까지 기다림(게이트가 오래 열려 시작을 막음), 실패를 횟수로만 셈(사용자 잘못이 아닌데 다시 물음) | spec 003 R-211, PRD FR-14 |
| 게이트는 넘길 수 있고 기록은 메모리에만(debate 3:0, 무인 실행 2026-11-10, 사람 확인 대기) | 넘기기 없이 통과까지 강제(재판정 동안 시작이 막히고, 빠져나가려고 아무 줄이나 세 번 적어 첫 행동과 판단 입력이 더러워짐), 안내만 하고 시작하면 닫힘(입력 칸 Enter가 제출과 시작으로 겹침), 설정 표에 통과 해시 저장(사용자 DB에 남아 되돌리기 어려움), 첫 행동이 있으면 게이트 없음(체크포인트 첫 행동도 판정 대상이라는 PRD와 어긋남) | 2026-11-10 debate 기록(로컬 `.audit/debate/`) |
| 게이트는 시작 전에만 | 도는 중에도(일하는 중 입력을 끊음), 시작 버튼을 눌렀을 때(시간 칩 고른 뒤 막힘) | 용어집 초안·현재 할 일 |
| 손해 칸은 판단 결과가 없으면 뺌 | "모름" 표시(세 칸 수용 기준은 지키나 빈 정보), 마감으로 손해 짐작(확률 지어내기) | spec 003 R-211 |
| 온보딩 키는 단계에서 바로 저장 | "시작하기"에서 함께 저장(Keychain 실패를 끝내기 실패로 묶어 온보딩이 다시 나옴) | spec 002 R-116, spec 003 R-213 |
| 키 확인 표시는 펼친 노치와 할 일 탭 | 기본 탭만(지금 상태, 사용자 지적), 알림 창(alert는 범위 밖) | 2026-11-10 사용자 지적 |

위험:

- 위험 1(일정): 검증 시작일 2026-11-10이 오늘이고 마일스톤 4·5가 남았다. 필수는 R-301~R-312(FR-04·FR-13, P0 수용 기준)다. 밀리면 R-313~R-315(온보딩 키 단계, 새 사용자만) 다음 R-316~R-318(키 확인 표시) 순으로 다음 spec에 넘긴다.
- 위험 2(게이트 기다림): 하루가 바뀐 직후나 일정을 고친 직후 모든 할 일을 다시 묻는 동안, 게이트 할 일은 이미 판단 결과가 있어 다시 물을 할 일 순서에서 뒤에 선다(spec 003 data-model §6 "판단 결과 없는 할 일 먼저", spec 003 위험 9). 할 일이 많으면 질의 한 번의 상한 3초가 여러 차례 쌓인 만큼 게이트가 기다릴 수 있다(동시 질의는 4개까지). 줄 앞으로 당기려면 spec 003 순서 규칙을 바꿔야 하며, 이 spec은 바꾸지 않는다.
- 위험 3(첫 행동 쓰는 곳이 둘): 지금 첫 행동은 체크포인트 다음 할 일 줄만 쓴다(spec 002 시안 9번 "체크포인트에서만 바뀜"). 게이트가 둘째로 쓰면 체크포인트가 게이트 줄을 덮을 수 있다. 마지막에 쓴 값을 남기는 것이 R-109와 같은 규칙이다.
- 위험 4(라벨 공백): 게이트 입력은 행동 로그에 남지 않아 FR-18 튜닝에서 concrete 질문의 사용자 라벨로 쓸 수 없다. 기록하려면 새 사용자 행동 값이 필요하고 승인 항목이다.
- 위험 5(개인정보): 게이트에서 적은 첫 행동이 판단 입력으로 외부 판단 모델에 간다. 이미 spec 003에서 첫 행동을 보내고 있으므로 새 노출은 아니다. 로그에는 남기지 않는다.
- 위험 6(사람 확인): 온보딩 키 단계는 새 사용자 첫 실행에만 보여 사람이 macOS 새 사용자 계정을 만들어 확인해야 한다(spec 003 R14가 온보딩 키 단계를 미룬 이유). 에이전트는 실제 앱 DB를 지우거나 열지 않는다.
- 위험 7(PRD와 다름): 재판정이 질문 넷인 점, 손해 칸 말이 "조금/꽤/아주"인 점, 게이트를 시작 전에만 여는 점은 PRD 6장·FR-13 글자와 다르다. PRD는 저장소 밖 문서라 고칠 문장을 사람에게 알린다.
